# Tomo III — UC-279

## TrackPrice.ai: Gemelos Digitales de Pricing Multiagente

UC-279 implementa un gemelo digital por SKU que conserva un estado vivo del mercado y coordina seis agentes especializados para observar, estimar, optimizar, detectar riesgos y decidir cambios de precio. El pipeline es determinista, auditable y seguro por defecto: una recomendación no modifica el precio salvo que se solicite `execute=true` y pase todos los guardrails.

## Los seis agentes

1. **Alpha — Tendencias**: medias móviles, momentum y dirección del mercado.
2. **Beta — Competencia**: gap competitivo, posicionamiento premium/discount y alertas.
3. **Gamma — Demanda**: estima elasticidad precio-demanda mediante regresión log-log, incluyendo confianza basada en ajuste e historial.
4. **Delta — Optimización**: maximiza profit o revenue mediante búsqueda global dentro de límites comerciales.
5. **Epsilon — Anomalías**: identifica desviaciones por z-score y bloquea automatizaciones riesgosas.
6. **Zeta — Estrategia**: sintetiza señales, confianza y riesgos; decide `increase`, `decrease`, `hold` o `review`.

Los agentes no comparten atributos globales. Cada uno emite un `AgentSignal` tipado; el Core entrega esas señales de forma explícita al siguiente agente.

## Estado vivo y concurrencia

Cada gemelo mantiene:

- SKU, precio, costo, precio competidor, demanda e inventario.
- Elasticidad y observaciones históricas.
- `version` para concurrencia optimista.
- Revenue, profit y margen derivados.
- Historial de ciclos y hashes de auditoría.

Al ingerir una observación se puede enviar `expected_version`. Si otro proceso actualizó el gemelo, la API devuelve conflicto de versión y evita sobrescribir datos recientes.

## Optimización y guardrails

La demanda se modela como:

```text
Q(p) = Q0 * (p / p0)^elasticity * scenario_demand_multiplier
```

La optimización evalúa una malla global entre límites calculados por:

- Precio mínimo: costo más margen mínimo.
- Separación máxima respecto al competidor.
- Cambio máximo frente al precio vigente.
- Inventario disponible.
- Objetivo seleccionable: `profit` o `revenue`.

La ejecución automática requiere:

- Confianza agregada mayor al umbral.
- Ausencia de anomalías críticas.
- Cambio material mayor a 0.2%.
- Precio dentro de todos los límites configurados.

## Escenarios soportados

| Escenario | Uso |
|---|---|
| `baseline` | Condiciones esperadas |
| `optimistic` | Mayor demanda y fortaleza competitiva |
| `pessimistic` | Contracción moderada |
| `competitor_shock` | Recorte agresivo de la competencia |
| `demand_shock` | Caída severa de demanda |

El forecast produce precio, demanda central, banda inferior/superior y profit esperado para 1–365 horizontes.

`POST /api/v1/twins/{sku}/forecast`

```json
{"days": 30, "scenario": "pessimistic", "price": 240.0}
```

La salida contiene `forecast[]` con `horizon`, `price`, `demand`, `lower_demand`, `upper_demand` y `expected_profit`.

## Consideraciones de producción

El registry actual es deliberadamente in-process para mantener el caso autocontenido. Para despliegue distribuido:

- Persistir estados/eventos en PostgreSQL o un event store.
- Sustituir el lock local por compare-and-swap transaccional.
- Alimentar observaciones desde streams (Kafka/Pub/Sub).
- Versionar modelos de elasticidad y monitorizar drift.
- Añadir aprobación humana para categorías reguladas.
- Incorporar stock-outs, promociones, impuestos, segmentación y canibalización entre SKUs.
