# UC-322 Cerebro AGI Multi-Agente Multi-Dominio Para Resolución Óptima de Conflictos
## AI-Native Operations & Agentic Patterns — TomoIII

**USO:** INTERNO PATENTADO

**Propósito:**
Capa AGI de resolución de conflictos que envuelve al cerebro AGI (UC-315) con un sistema de 4 niveles para gestionar disputas entre agentes autónomos. Implementa mecanismos que un sistema real necesita: evitar bloqueos, prevenir trabajo duplicado, mantener progreso. Un cerebro AGI de trading no necesita equilibrio de Nash teórico; necesita no quedarse colgado cuando dos agentes discrepan.

**Principio arquitectónico:**

> UC-315 decide, UC-317 ejecuta, UC-324 contiene, **UC-322 resuelve conflictos entre agentes**.

---

## Arquitectura de Resolución de Conflictos

```
Conflicto detectado (GWT o MetacognitiveMonitor)
    │
    ├── Nivel 1: Negociación directa entre agentes
    │     └── Intercambio de creencias + concesiones graduales
    │
    ├── Nivel 2: Votación ponderada por reputación dinámica
    │     └── Reputación se actualiza con cada episodio
    │
    ├── Nivel 3: CNP con pujas dinámicas por la tarea
    │     └── Score = bid + confianza + reputación - costo - latencia
    │
    └── Nivel 4: Escalación al GeneralOrchestrator
          └── MetacognitiveMonitor decide PROCEED/REVIEW/STOP/REASSIGN
```

**Orden de implementación:**

1. **Reputación dinámica en CNP** (mayor impacto, menor complejidad)
2. **Negociación con concesiones** (reemplazar validación binaria de Juice)
3. **Protocolo de escalación formal** (formaliza lo que UC-315 ya hace implícitamente)
4. **Detección de trabajo duplicado y bloqueos** (operacional, previene stall)

## Observaciones

Los sistemas multiagente gestionan la resolución de conflictos mediante mecanismos como la negociación, la asignación de prioridades, la votación y los protocolos de consenso. Los agentes pueden diseñarse para compartir creencias o intenciones, mediar en el acceso a recursos compartidos o escalar los conflictos no resueltos a un agente orquestador o mediador de nivel superior. Los sistemas avanzados pueden utilizar puntuaciones de reputación o confianza para ponderar la información aportada por los agentes o implementar protocolos de red contractual donde los agentes pujan dinámicamente por la propiedad de las tareas. Estas técnicas ayudan a minimizar los bloqueos, evitar el trabajo duplicado y garantizar que el ecosistema multiagente mantenga el progreso y la equidad, incluso cuando los agentes tienen objetivos superpuestos u operan de forma semiindependiente.

## Núcleo de Ejecución Resiliente

Para abordar las limitaciones arquitectónicas de los agentes autónomos (falta de memoria, orquestación frágil y errores inmaduros), UC-322 integra un **Núcleo de Ejecución Resiliente** que envuelve al agente en un bucle con reintentos, memoria persistente y trazas estructuradas en formato OpenTelemetry (Logs para Loki, Spans para Tempo, Métricas para Prometheus).

### Cómo este algoritmo resuelve los problemas descritos:

1. **Falta de Memoria Persistente:** El sistema de reputación mantiene estado entre sesiones. Cada episodio se registra y afecta la reputación futura del agente.
2. **Soporte Limitado de Orquestación:** Los 4 niveles de resolución implementan reintentos estructurados. Si el Nivel 1 falla, se escala al Nivel 2, luego al 3, y finalmente al 4.
3. **Manejo Inmaduro de Errores:** El protocolo de escalación categoriza conflictos por severidad y aplica estrategias específicas (PROCEED, REVIEW, STOP, REASSIGN).
4. **Trazas y Depuración:**
   - **Para Logs (Loki):** El `ObservabilityManager` genera JSON con `trace_id`, `span_id` y `parent_span_id`. En Grafana Loki, usar el LogQL `| json | line_format "{{.message}}"` permite filtrar por `trace_id`.
   - **Para Spans (Tempo):** Los spans jerárquicos permiten ver el grafo completo: cómo el span de negociación falló, lo que forzó el span de votación, y finalmente el span de escalación.
   - **Para Métricas (Prometheus):** Los contadores por nivel permiten visualizar "Tasa de Resolución por Nivel" y "Veredictos de Escalación".

## Conceptos clave

| Concepto | Función | Ejemplo en trading |
|---|---|---|
| **Negociación con concesiones** | Agentes intercambian creencias y ceden gradualmente | Technical (0.85) y Sentiment (0.40) negocian hasta converger |
| **Votación ponderada por reputación** | El peso del voto depende del historial del agente | Technical (rep=0.95) tiene más peso que Risk (rep=0.50) |

| **Escalación formal** | Conflictos no resueltos van al GeneralOrchestrator | MetacognitiveMonitor decide STOP tras 3 conflictos consecutivos |
| **Reputación dinámica** | Se actualiza tras cada episodio (éxito/fallo) | Agent que falla 3 veces baja de 0.80 a 0.50 |
| **Detección de duplicados** | Evita que dos agentes hagan la misma tarea | Fingerprint hash detecta "Comprar AAPL" duplicado |
| **Detección de deadlocks** | Detecta ciclos de espera entre agentes | A espera B, B espera A → circuit breaker |

## Componentes

### 1. `ConflictResolutionLayer` (UC-322.py)

Orquestador principal que coordina los 4 niveles de resolución en orden ascendente:

- Si el Nivel 1 (negociación) resuelve → retorna sin escalar.
- Si no → Nivel 2 (votación).
- Si no → Nivel 3 (CNP).
- Si no → Nivel 4 (escalación al GeneralOrchestrator).

Además:
- Registra episodios en el sistema de reputación tras cada resolución.
- Emite spans, logs y métricas para observabilidad.
- Detecta trabajo duplicado y deadlocks.

### 2. `ReputationSystem` (reputation_system.py)

Sistema de reputación dinámica que reemplaza el `reliability` estático del CNP original.

**Fórmula de reputación:**

```
reputation = clamp(
    0.50                              # base
    + 0.30 * success_rate             # éxito histórico
    + 0.15 * avg_quality              # calidad promedio
    + 0.05 * avg_efficiency           # eficiencia promedio
    - 0.10 * recent_failures          # penalización por fallos recientes
, 0.0, 1.0)
```

La reputación se actualiza tras cada episodio. Los agentes con mejor historial tienen mayor peso en votaciones y pujas CNP.

### 3. `NegotiationEngine` (negotiation_engine.py) — Nivel 1

Reemplaza la validación binaria de Juice (aprobar/bloquear) con un protocolo de negociación donde:

- Cada agente propone su posición inicial (confidence).
- En cada ronda, cada agente hace una concesión proporcional a:
  - Su flexibilidad (inverso de su confianza).
  - La reputación del otro agente.
  - El número de ronda (concesiones mayores en rondas tempranas).
- Si la brecha (gap) cae bajo el umbral → acuerdo.
- Si se agotan las rondas → escalar al Nivel 2.

### 4. `VotingSystem` (voting_system.py) — Nivel 2

Votación ponderada por reputación dinámica. Reemplaza el voto ponderado estático (0.35/0.25/0.15) del `trading_agents.py` original.

- El peso del voto = `reputación * confianza_en_la_opción`.
- La opción con mayor peso total gana.
- Si el ganador supera el umbral de consenso (default: 0.60) → acuerdo.
- Si no → escalar al Nivel 3.

### 5. `DynamicCNP` (cnp_dynamic.py) — Nivel 3

Contract Net Protocol con pujas dinámicas y reputación. Extiende el CNP original con:

**Fórmula de adjudicación:**

```
composite_score = 0.35 * bid_score
                + 0.25 * confidence
                + 0.25 * reputation
                - 0.10 * estimated_cost
                - 0.05 * normalized_latency
```

El agente con el mayor score compuesto se adjudica la tarea, si supera el mínimo (default: 0.30).

### 6. `EscalationProtocol` (escalation_protocol.py) — Nivel 4

Protocolo formal de escalación al orquestador de nivel superior (GeneralOrchestrator / MetacognitiveMonitor).

**Veredictos:**

| Veredicto | Condición | Acción |
|---|---|---|
| `PROCEED` | Severidad baja, negociación casi acordó | Continuar con mejor opción |
| `REVIEW` | Severidad alta, sin resolución clara | Pausar, solicitar revisión humana |
| `STOP` | Circuit breaker abierto o severidad crítica | Detener operaciones del dominio |
| `REASSIGN` | CNP encontró ganador | Reasignar tarea al ganador |

**Circuit breaker:** Se abre tras 3 conflictos consecutivos no resueltos. Detiene todas las operaciones hasta reset manual.

### 7. `DuplicateDetection` (duplicate_detection.py)

Detecta trabajo duplicado usando fingerprints (hash SHA-256 de la descripción normalizada).

- Registra tareas activas con fingerprint.
- Si una tarea nueva coincide con una activa (mismo dominio, diferente agente) → conflicto.
- Las tareas completadas se remueven del registry.

### 8. `DeadlockDetector` (duplicate_detection.py)

Detecta deadlocks usando detección de ciclos en el grafo de espera.

- Si Agente A espera a B, y B espera a A → ciclo → deadlock.
- Usa DFS para encontrar ciclos.
- También detecta stalls (tareas sin progreso por >30s).

### 9. `ObservabilityManager` (observability.py)

Gestiona métricas, logs y trazas:

- **Métricas Prometheus:** Contadores por nivel de resolución, por resultado, por veredicto.
- **Logs Loki:** JSON con `trace_id`, `agent_id`, `level`, `message`.
- **Trazas Tempo:** Spans jerárquicos con `parent_span_id` para ver el árbol de resolución.

Endpoint `/metrics` expone métricas en formato Prometheus text.

### Relación con UC-324 (Containment)

UC-322 no modifica el cerebro cognitivo (UC-315). Las resoluciones de UC-322 son **evidencia**, no órdenes. Las acciones de efecto externo siguen pasando por UC-324 (PRE/EXEC/POST gates).

```
UC-315 detecta conflicto → UC-322 resuelve → UC-324 valida la acción resultante
```

## Gobernanza y límites

- UC-322 es una capa de resolución de conflictos, no un cerebro cognitivo.
- Las resoluciones de UC-322 son evidencia para UC-315, no órdenes directas.
- Las acciones de efecto externo (pagos, órdenes, cancelaciones) siempre pasan por UC-324.
- El circuit breaker puede detener todas las operaciones del dominio si hay conflictos consecutivos.
- Toda resolución queda registrada con trace_id para trazabilidad completa.
- La reputación dinámica asegura que los agentes con mejor historial tengan mayor influencia.

## Despliegue en Producción — Guía Paso a Paso

Esta sección describe cómo desplegar UC-322 en un entorno de producción integrado con el ecosistema AGI completo: UC-315 (cerebro cognitivo), UC-317 (kernel de ejecución), UC-324 (contención y gobernanza).

### Principio Arquitectónico Fundamental

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│   UC-315 DECIDE → UC-322 RESUELVE → UC-324 CONTIENE → UC-317 EJECUTA      │
│                                                                             │
│   "Un modelo genera evidencia. La evidencia no es una orden."               │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

Las resoluciones de UC-322 son **evidencia** para UC-315, no órdenes directas. Las acciones de efecto externo (pagos, órdenes de trading, cancelaciones) siempre pasan por UC-324 antes de que UC-317 las ejecute.

### Paso 4: Flujo Completo de Resolución de Conflictos en Producción

Este es el flujo paso a paso que ocurre cuando múltiples agentes de UC-315 generan propuestas contradictorias:

```
┌──────────────────────────────────────────────────────────────────────────┐
│  FLUJO DE PRODUCCIÓN: RESOLUCIÓN DE CONFLICTOS MULTI-AGENTE            │
├──────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  1. UC-315: Agentes generan creencias/propuestas                        │
│     ├── TechnicalAnalyst.analyze(snapshot) → BUY AAPL conf=0.85         │
│     ├── SentimentAnalyst.analyze(snapshot) → SELL AAPL conf=0.70        │
│     ├── RiskAgent.validate(signal) → issues: ["volatility_high"]        │
│     └── FundamentalAnalyst.analyze(snapshot) → HOLD conf=0.55           │
│                                                                          │
│  2. UC-315: GlobalWorkspace detecta conflicto                           │
│     └── workspace.broadcast["flags"] contiene "conflict_detected"       │
│                                                                          │
│  3. UC-322: Recibe creencias y ejecuta pipeline de 4 niveles            │
│     ├── Nivel 1: NegotiationEngine intenta concesiones                  │
│     │   └── Technical (0.85) y Sentiment (0.70) negocian 5 rondas       │
│     │   └── Si gap < threshold → ACUERDO → ir a paso 7                  │
│     ├── Nivel 2: VotingSystem con reputación dinámica                   │
│     │   └── Voto ponderado: rep(technical)=0.92 × conf=0.85 = 0.782    │
│     │   └── Si consenso > 0.60 → ACUERDO → ir a paso 7                 │
│     ├── Nivel 3: DynamicCNP con pujas                                   │
│     │   └── Score = 0.35×bid + 0.25×conf + 0.25×rep - 0.10×cost        │
│     │   └── Si ganador > min_composite → ADJUDICACIÓN → ir a paso 7    │
│     └── Nivel 4: EscalationProtocol                                     │
│         └── Evalúa severidad → PROCEED|REVIEW|STOP|REASSIGN            │
│         └── Si STOP → circuit breaker → detener dominio                 │
│         └── Si REVIEW → solicitar revisión humana                       │
│                                                                          │
│  4. UC-322: Actualiza reputación del agente ganador/perdedor            │
│     └── ReputationSystem.record_episode(agent, success, quality, eff)   │
│                                                                          │
│  5. UC-322: Emite observabilidad                                        │
│     ├── Log JSON → Loki (trace_id, agent_id, level, veredicto)          │
│     ├── Span jerárquico → Tempo (negotiation → voting → cnp → escal)   │
│     └── Contador Prometheus → conflict_negotiation_total{result=...}    │
│                                                                          │
│  6. UC-322: Retorna resolución como EVIDENCIA (no como orden)           │
│     └── ConflictResolutionResult con level_reached, success, winner     │
│                                                                          │
│  7. UC-324: PRE gate valida la acción resultante                        │
│     ├── Capa A: AGTGovernanceAdapter → roles, permisos, riesgo          │
│     ├── Capa C: AISafetyRedTeamAdapter → jailbreak, prompt injection    │
│     ├── Capa E: AwesomeSafetyCIAdapter → umbral de confianza            │
│     ├── Capa G: AgentPolicyEngineAdapter → proveniencia del contenido   │
│     ├── Capa I: OpenGuardrailsAdapter → PII, allowlist de modelos       │
│     └── SafetyCriticalMonitor → circuit breaker por skill               │
│     └── Si blocked → DETENER, registrar en audit log                    │
│                                                                          │
│  8. UC-324: EXEC gate firma la intención                                │
│     └── Capa F: FarameshCryptoBoundaryAdapter                           │
│         ├── HMAC-SHA256 con nonce + timestamp                           │
│         ├── Anti-replay (nonce ya usado → rechazar)                     │
│         └── Patrones peligrosos (rm -rf, DROP TABLE → rechazar)         │
│                                                                          │
│  9. UC-317: Ejecuta la acción autorizada                                │
│     ├── AgentKernel.create_session(agent_id, model, roles)              │
│     ├── AgentKernel.syscall(SyscallRequest) o .chat(agent_id, msg)      │
│     ├── LLMCore enruta a backend: OpenAI | Ollama | Mock               │
│     ├── ToolManager ejecuta herramientas si LLM las solicita            │
│     ├── MemoryManager persiste contexto y resultado                     │
│     └── Retorna resultado a UC-324                                      │
│                                                                          │
│ 10. UC-324: POST gate audita el resultado                               │
│     ├── Capa D: SafeAutoPostActionAdapter → reglas declarativas         │
│     ├── Capa J: AgentDoGEvalAdapter → riesgo de trayectoria            │
│     ├── Capa K: OpenAgentSafetyEvalAdapter → stage-wise safety          │
│     └── Si POST falla en modo ENFORCE → marcar plan como blocked        │
│                                                                          │
│ 11. Feedback: Resultados regresan al ecosistema                         │
│     ├── UC-315: MetacognitiveMonitor.observe_internal_state()           │
│     │   └── Actualiza coherencia, detecta anomalías                     │
│     │   └── Emite veredicto: PROCEED | REVIEW | STOP                   │
│     ├── UC-315: GlobalWorkspace.broadcast(persist=True)                 │
│     │   └── Persiste hipótesis ganadora en memoria episódica            │
│     ├── UC-322: ReputationSystem.record_episode()                       │
│     │   └── Actualiza reputación del agente según éxito/fallo           │
│     └── UC-322: _resolution_history.append(result)                      │
│         └── Historial consultable vía GET /api/v1/conflicts/history     │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘
```

### Paso 5: Integración Programática entre Componentes

#### 5.1 UC-315 → UC-322: Enviar creencias conflictivas

Cuando UC-315 detecta un conflicto (vía `GlobalWorkspace` o `MetacognitiveMonitor`), envía las creencias a UC-322:

```python
import requests

# UC-315 detecta conflicto entre agentes
beliefs = [
    {"agent_id": "technical",   "proposition": "BUY AAPL",  "confidence": 0.85},
    {"agent_id": "sentiment",   "proposition": "SELL AAPL", "confidence": 0.70},
    {"agent_id": "risk",        "proposition": "HOLD AAPL", "confidence": 0.60},
    {"agent_id": "fundamental", "proposition": "BUY AAPL",  "confidence": 0.55},
]

# Enviar a UC-322 para resolución
response = requests.post(
    "http://localhost:5322/api/v1/conflicts/resolve",
    json={
        "beliefs": beliefs,
        "domain": "trading",
        "options": ["BUY", "SELL", "HOLD"],
        "task_id": "trade-AAPL-20250101-001",
    }
)
resolution = response.json()
# resolution["data"]["level_reached"]  → "NEGOTIATION" | "VOTING" | "CNP_BIDDING" | "ESCALATION"
# resolution["data"]["success"]        → True | False
```

#### 5.2 UC-322 → UC-324: Validar acción resultante

La resolución de UC-322 es evidencia. Antes de ejecutar, UC-324 valida:

```python
# La resolución de UC-322 produce una acción propuesta
resolved_action = {
    "skill_name": "MarketExecutionSkill",
    "inputs": {
        "symbol": "AAPL",
        "side": "BUY",
        "quantity": 100,
        "price": 150.00,
    },
    "user_roles": ["trader", "user"],
    "domain": "trading",
}

# PRE gate: validar antes de ejecutar
pre_response = requests.post(
    "http://localhost:5299/api/v1/containment/check",
    json={
        "skill_name": resolved_action["skill_name"],
        "inputs": resolved_action["inputs"],
        "user_roles": resolved_action["user_roles"],
        "domain": resolved_action["domain"],
    }
)
pre_result = pre_response.json()

if not pre_result["data"]["allowed"]:
    # UC-324 bloqueó la acción
    print(f"BLOQUEADO: {pre_result['data']['issues']}")
    # Registrar en UC-322 como fallo
    requests.post("http://localhost:5322/api/v1/reputation/record", json={
        "agent_id": "technical",  # agente que propuso la acción
        "task_id": "trade-AAPL-20250101-001",
        "success": False,
        "quality": 0.0,
        "efficiency": 0.0,
        "domain": "trading",
    })
else:
    # Continuar a EXEC gate y UC-317
    pass
```

#### 5.3 UC-324 → UC-317: Ejecutar acción autorizada

```python
# Firmar intención (EXEC gate)
sign_response = requests.post(
    "http://localhost:5299/api/v1/containment/sign-intent",
    json={
        "skill_name": "MarketExecutionSkill",
        "action_class": "execute",
        "inputs": resolved_action["inputs"],
    }
)
signature = sign_response.json()["data"]["signature"]
nonce = sign_response.json()["data"]["nonce"]

# Crear sesión en UC-317
session_response = requests.post(
    "http://localhost:5317/api/v1/kernel/sessions",
    json={
        "name": "trade-executor",
        "roles": ["user", "trader"],
        "model": "openai",  # o "ollama" para ejecución local
        "system_prompt": "Ejecutar orden de trading autorizada por UC-324.",
    }
)
agent_id = session_response.json()["data"]["agent_id"]

# Ejecutar vía syscall
exec_response = requests.post(
    "http://localhost:5317/api/v1/kernel/syscall",
    json={
        "agent_id": agent_id,
        "operation": "tool.call",
        "payload": {
            "name": "market_execute",
            "args": resolved_action["inputs"],
        },
        "trace_id": "trade-AAPL-20250101-001",
    }
)
exec_result = exec_response.json()
```

#### 5.4 Feedback: Resultados → UC-322 + UC-315

```python
# Registrar resultado en UC-322 (reputación)
success = exec_result["data"]["success"]
requests.post("http://localhost:5322/api/v1/reputation/record", json={
    "agent_id": "technical",
    "task_id": "trade-AAPL-20250101-001",
    "success": success,
    "quality": 0.85 if success else 0.20,
    "efficiency": 0.90 if success else 0.30,
    "domain": "trading",
})

# POST gate en UC-324 (auditoría post-ejecución)
post_response = requests.post(
    "http://localhost:5299/api/v1/containment/post-check",
    json={
        "skill_name": "MarketExecutionSkill",
        "inputs": resolved_action["inputs"],
        "output": exec_result["data"],
        "trajectory": [],
    }
)
# Si POST gate falla → registrar anomalía, considerar rollback
```

### Paso 6: Puntos de Integración Detallados con UC-315

UC-322 se conecta con los siguientes componentes del cerebro AGI (UC-315):

#### 6.1 GeneralOrchestrator (Nivel 4 de Escalación)

```
GeneralOrchestrator.validate_and_execute(plan)
    │
    ├── Antes: UC-322 puede resolver conflictos en el plan
    │   └── resolve_plan_conflicts(plan) → detectar pasos mutuamente excluyentes
    │
    ├── Durante: SafetySupervisor315.check() por cada paso
    │   └── Si blocked → UC-322 puede reasignar agente vía CNP dinámico
    │
    └── Después: UC-322 registra episodio y actualiza reputación
```

- **Archivo:** `general_orchestrator.py` (líneas 119-161)
- **Método clave:** `validate_and_execute(plan, user_roles, domain_state, auto_approve)`
- **Integración:** UC-322 actúa como mediador cuando `_aggregate_plan_status(plan)` retorna `blocked` o `failed` debido a conflictos entre pasos.

#### 6.2 MetacognitiveMonitor (Señales de Escalación)

```
MetacognitiveMonitor.observe_internal_state()
    │
    ├── coherence < 0.5 → UC-322 investiga conflicto entre agentes
    │
    ├── anomalies: ["broadcast_flag:conflict"] → UC-322 resuelve
    │
    └── verdict: "STOP" → UC-322 abre circuit breaker del dominio
```

- **Archivo:** `metacognitive_monitor.py` (líneas 38-94)
- **Veredictos:** `_map_verdict()` retorna `PROCEED | REVIEW | STOP` (líneas 113-121)
- **Integración:** Los veredictos `REVIEW` y `STOP` son señales naturales para activar la resolución de conflictos de UC-322.

#### 6.3 GlobalWorkspace (Detección de Conflictos GWT)

```
GlobalWorkspace.broadcast(workspace)
    │
    ├── workspace.selected_hypothesis → hipótesis ganadora
    │
    ├── workspace.broadcast["flags"] → puede contener "conflict_detected"
    │
    └── Hipótesis alternativas (runner-ups) → UC-322 puede re-evaluar
```

- **Archivo:** `global_workspace.py` (líneas 52-82)
- **Integración:** UC-322 lee `selected_hypothesis` y las hipótesis descartadas. Si dos hipótesis de alta confianza son mutuamente excluyentes, UC-322 inicia la negociación.

#### 6.4 ContractNetMiddleware (CNP Original → CNP Dinámico UC-322)

```
ContractNetMiddleware.evaluate_and_award(round_)
    │
    ├── Score original: 0.5×bid + 0.3×conf - 0.1×cost - 0.1×latency
    │
    └── UC-322 reemplaza con: 0.35×bid + 0.25×conf + 0.25×rep - 0.10×cost - 0.05×latency
        └── rep = ReputationSystem.get_reputation(agent_id, domain)
```

- **Archivo:** `cnp_broadcast_middleware.py` (líneas 195-201)
- **Integración:** UC-322 proporciona `ReputationSystem` que reemplaza el `reliability` estático del CNP original con reputación dinámica basada en historial.

#### 6.5 JuiceValidator (Validación Binaria → Negociación)

```
JuiceValidator._local_validate(signal, snapshot)
    │
    ├── Original: consensus = mean(agent_scores), approved = consensus >= 0.55
    │
    └── UC-322: NegotiationEngine con concesiones graduales
        ├── Ronda 1: intercambio de posiciones
        ├── Ronda 2-5: concesiones proporcionales a flexibilidad × reputación
        └── Si gap < threshold → acuerdo con matices (no binario)
```

- **Archivo:** `juice_agents.py` (líneas 160-183)
- **Integración:** UC-322 reemplaza la validación aprobar/bloquear con un protocolo de negociación donde los agentes ceden gradualmente.

#### 6.6 TraderAgent (Voto Estático → Voto Dinámico)

```
TraderAgent.generate_signal()
    │
    ├── Original: pesos fijos (technical=0.35, sentiment=0.25, fundamental=0.15)
    │
    └── UC-322: VotingSystem con peso = reputación × confianza
        └── Agent con rep=0.95 tiene 2× el peso de agent con rep=0.50
```

- **Archivo:** `trading_agents.py` (líneas 162-187)
- **Integración:** UC-322 reemplaza los pesos fijos con pesos dinámicos basados en el historial de cada agente por dominio.

### Paso 10: Circuit Breakers y Respuesta a Incidentes

#### 10.1 Circuit Breaker de UC-322

El circuit breaker se abre tras 3 conflictos consecutivos no resueltos en un dominio:

```
Estado normal (cerrado)
    │
    ├── Conflicto no resuelto #1 → contador++
    ├── Conflicto no resuelto #2 → contador++
    ├── Conflicto no resuelto #3 → CIRCUIT BREAKER ABIERTO
    │   └── Todas las operaciones del dominio se detienen
    │   └── Alerta "CircuitBreakerAbierto" (severity: critical)
    │   └── Veredicto de escalación: STOP
    │
    └── Reset manual requerido:
        POST /api/v1/escalation/circuit-breaker/reset
```

#### 10.2 Circuit Breaker de UC-324

UC-324 tiene su propio `SafetyCriticalMonitor` con circuit breakers por skill:

```
CircuitBreakerState: CLOSED → OPEN → HALF_OPEN → CLOSED
    │
    ├── failure_count > threshold → OPEN (bloquea ejecución)
    ├── Tras cooldown → HALF_OPEN (permite 1 intento)
    └── Si éxito → CLOSED, si fallo → OPEN
```

#### 10.3 Kill Switch Global

UC-324 expone un kill switch que detiene **toda** la ejecución:

```bash
# Activar kill switch (emergencia)
curl -X POST http://localhost:5299/api/v1/containment/kill-switch \
  -H "Content-Type: application/json" \
  -d '{"action": "kill"}'

# Verificar estado
curl http://localhost:5299/health
# → {"killed": true, ...}

# Desactivar kill switch (requiere autorización)
curl -X POST http://localhost:5299/api/v1/containment/kill-switch \
  -H "Content-Type: application/json" \
  -d '{"action": "unkill"}'
```

#### 10.4 Procedimiento de Respuesta a Incidentes

```
1. DETECTAR
   ├── Alerta Prometheus: AltaTasaDeConflictos | CircuitBreakerAbierto
   ├── Dashboard Grafana: panel "Circuit Breaker Status" en rojo
   └── Log Loki: {job="uc322"} |= "STOP" | json

2. CONTENER
   ├── Si dominio específico: resetear circuit breaker de UC-322
   │   POST /api/v1/escalation/circuit-breaker/reset
   ├── Si sistémico: activar kill switch de UC-324
   │   POST /api/v1/containment/kill-switch {"action": "kill"}
   └── Notificar equipo de operaciones

3. INVESTIGAR
   ├── Consultar historial: GET /api/v1/conflicts/history
   ├── Consultar escalaciones: GET /api/v1/escalation/history
   ├── Consultar audit log: GET /api/v1/containment/audit (UC-324)
   ├── Filtrar logs por trace_id en Loki
   └── Revisar spans jerárquicos en Tempo/Grafana

4. RESOLVER
   ├── Identificar agente(s) causante(s)
   ├── Ajustar reputación si es necesario (manual)
   ├── Verificar que el conflicto subyacente se resolvió
   └── Desactivar kill switch / resetear circuit breaker

5. PREVENIR
   ├── Actualizar umbrales de negociación si fueron muy estrictos
   ├── Ajustar consensus_threshold en VotingConfig
   ├── Revisar min_composite_score en CNPConfig
   └── Documentar el incidente
```

### Paso 12: Seguridad en Producción

#### 12.1 Secretos y Credenciales

| Secreto | Variable de Entorno | Propósito |
|---|---|---|
| HMAC crypto | `UC324_CRYPTO_SECRET` | Firma de intenciones EXEC gate |
| HMAC crypto | `FARAMESH_SECRET` | Anti-replay y verificación |
| OpenAI API | `OPENAI_API_KEY` | Backend LLM de UC-317 |
| Grafana API | `GRAFANA_API_KEY` | Importar dashboards |

Nunca almacenar secretos en código o archivos de configuración. Usar un gestor de secretos (Vault, AWS Secrets Manager, etc.) o variables de entorno inyectadas por el orquestador de contenedores.

#### 12.2 RBAC (UC-317)

UC-317 implementa control de acceso basado en roles:

| Rol | Permisos | Riesgo máximo |
|---|---|---|
| `guest` | `llm:call`, `memory:read` | low |
| `user` | + `tool:use`, `memory:write`, `agent:run` | medium |
| `developer` | + `storage:*`, `agent:schedule` | high |
| `admin` | todos | critical |

En producción, restringir los roles `developer` y `admin`. Validar `allowed_risk` antes de crear sesiones.

#### 12.3 Frontera Criptográfica (UC-324)

Las acciones de clase `execute`, `transact` y `delete` requieren firma HMAC-SHA256:

```
Intención → HMAC(secreto, JSON_serializado) → signature + nonce + timestamp
    │
    ├── TTL: 60 segundos (configurable)
    ├── Anti-replay: nonce único (rechazar nonces ya usados)
    └── Patrones peligrosos: rechazar rm -rf, DROP TABLE, exec(), eval()
```

#### 14.2 Anti-patrones a Evitar

```
✗ NO tratar resoluciones de UC-322 como órdenes directas de ejecución
  → Las resoluciones son evidencia; siempre pasar por UC-324

✗ NO ejecutar UC-324 en modo AUDIT o DISABLED en producción
  → Usar ENFORCE para bloquear acciones inseguras

✗ NO usar secretos por defecto (uc324-default-secret)
  → Generar secretos criptográficamente aleatorios

✗ NO omitir el POST gate después de la ejecución
  → La auditoría post-ejecución detecta anomalías no previstas

✗ NO ignorar alertas de circuit breaker
  → Un circuit breaker abierto indica un problema sistémico

✗ NO crear loops infinitos de corrección
  → Limitar reintentos; escalar a humano si persiste

✗ NO asumir que tests locales equivalen a producción segura
  → Los tests validan lógica, no configuración de red/secretos/carga
```

✓ No-duplicados: Fingerprints SHA-256 detectan trabajo redundante
✓ Trazabilidad: Todo tiene trace_id, span_id, audit_log
