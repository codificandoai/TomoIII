## Descripción

UC-703 es el **runtime/orquestador unificado** del ecosistema AGI. Conecta las existentes UC y capas AGI:

| UC | Rol en el runtime |
|---|---|
| **UC-315** | Decide qué hacer |
| **UC-325** | Razona y verifica antes de decidir |
| **UC-326 / UC-296** | Recuerda contexto y episodios |
| **UC-290** | Aprueba intervenciones humanas (HITL) |
| **UC-300** | Gateway de herramientas, pre-intent y constitucional |
| **UC-317** | Ejecuta herramientas locales/sandbox |
| **UC-324** | Contiene/aisla si es necesario |
| **UC-075 / UC-309** | Entrenamiento continuo, incidentes y observabilidad |

UC-703 añade los **motores de ejecución durable y conectores externos**:

- **Temporal**: tareas largas que sobreviven a fallos (checkpointing, reintentos, señales, cancelación).
- **StackStorm**: reacción a eventos de infraestructura vía playbooks/runbooks.
- **n8n**: conexión rápida con apps SaaS (Slack, Salesforce, Notion, Jira, email).
- **Observability Bridge**: métricas, logs y trazas hacia UC-309 → Grafana Stack.
- **Fine-Tuning Lifecycle Controller**: agentes especializados para curación, leakage, recursos, SRE de entrenamiento, HP search, evaluación multi-juez, promotion gate, alineación, despliegue, canary, drift, alucinaciones y feedback loop.

### Filosofía de autoridad

> **UC-315 decide, UC-317 ejecuta, UC-703 orquesta.**

- UC-703 **nunca decide autónomamente**.
- El planner (por defecto un mock determinista) es reemplazable por UC-315/UC-325.
- Cada paso de ejecución requiere un `approval_ref` auditable.
- Acciones destructivas o de alto impacto exigen scope `hitl`.
- **Evidencia no es orden**: un LLM propone, pero la ejecución solo ocurre tras aprobación.

## Flujo de ejecución

```text
1. POST /api/v1/objective
   -> Crea RuntimeTask + Objective
2. POST /api/v1/objective/<task_id>/plan
   -> Llama al planner (UC-315/325 por inyección)
   -> Recupera contexto de memoria (UC-326/296)
3. POST /api/v1/objective/<task_id>/approve
   -> Cada paso solicita aprobación a UC-290/300
4. POST /api/v1/objective/<task_id>/execute
   -> Ejecuta cada paso en el backend correspondiente:
      - temporal:   tareas largas y migraciones
      - stackstorm: eventos de infra
      - n8n:        workflows SaaS
      - local:      herramientas sandbox UC-317
   -> Guarda checkpoints en LongTermTaskManager
   -> Sincroniza episodios con MemorySyncAdapter
   -> Emite observabilidad a UC-309
```

## Reglas de gobernanza

| Regla | Efecto |
|---|---|
| Sin `approval_ref` | Ejecución rechazada |
| Acción destructiva con scope `auto` | Rechazada; requiere `hitl` |
| Acción fuera de allowlist | Rechazada |
| Coste > $1000 o duración > 1h | Requiere HITL |
| Cross-tenant (tenant_id != target_tenant) | Requiere HITL |
| Timeout de tarea | Marcada como failed; último checkpoint disponible |

### Fine-Tuning Lifecycle

`FineTuningController` materializa el ciclo completo:

```text
Curación → Leakage audit → Versionado → Plan de recursos → HP search
    → Entrenamiento (SRE) → Evaluación multi-juez → Promotion gate
    → Alineación → Bundle → Canary → Drift/feedback → Closed-loop retrain
```

```text

    └── valida output antes de entregar al agente
         │
         ▼

         │
         ▼
RetryManager ──► reintento con backoff exponencial + jitter
    ├── solo repite paso fallido
    └── sin invalidar pasos completados
         │
         ▼
ContextRebuilder + ReplanningAgent
    ├── traza comprimida (pasos OK, estado parcial, causa raíz)
    └── fallback prompts: alternative_tool / simplify / split

    ├── logs estructurados con run_id, step, tool, error, policy, resultado
```
