# DESCRIPTION

Sistema autónomo de reentrenamiento continuo de modelos de ML: recolecta
datos de múltiples fuentes (feedback de usuarios, anotaciones humanas,
APIs externas), los filtra por calidad (longitud, spam, validez
lingüística, deduplicación semántica), decide autónomamente —según
umbrales configurables en `config/thresholds.yaml`— si corresponde un
reentrenamiento completo o un fine-tuning ligero, entrena el modelo
candidato, lo valida contra el modelo en producción (métricas +
robustez ante casos extremos) y, si supera los umbrales de calidad, lo
despliega de forma segura, conservando un respaldo del modelo anterior
para poder revertir (`rollback`) en caso de regresión. La telemetría de
uso en producción (`track_usage`) retroalimenta la base de conocimiento,
cerrando el ciclo de aprendizaje continuo.

| Etapa | Módulo | Qué hace |
|-------|--------|----------|
| **Ingesta** | `core.data_collector.DataCollector` | Normaliza y filtra datos de `user_feedback`, `annotations`, `external_api` |
| **Almacenamiento** | `core.knowledge_base.KnowledgeBase` | Única fuente de verdad (SQLite): datos, anotaciones, historial de modelos, telemetría de uso |
| **Disparo** | `pipeline_service.ContinuousLearningPipeline.check_retraining_trigger` | Decide `full_retraining` / `fine_tuning` / `no_training` según umbrales |
| **Entrenamiento** | `models.trainer.ModelTrainer` | Pipeline TF-IDF + RandomForest; entrenamiento completo o incremental |
| **Validación** | `core.model_validator.ModelValidator` | Métricas de clasificación + casos extremos + comparación con baseline |
| **Despliegue** | `core.deployment_manager.DeploymentManager` | Promoción a producción con respaldo automático y `rollback` |
| **Inferencia** | `pipeline_service.ContinuousLearningPipeline.predict` | Sirve el modelo desplegado y registra telemetría de uso |

## Endpoints del API Flask (`app.py`)

| Método | Ruta | Descripción |
|--------|------|-------------|
| GET | `/health` | Liveness/readiness probe. |
| POST | `/api/v1/data/ingest` | Ingiere y filtra datos desde múltiples fuentes. |
| POST | `/api/v1/data/validate` | Aprueba muestras ingeridas para entrenamiento. |
| POST | `/api/v1/training/run` | Ejecuta entrenamiento (completo/fine-tuning/automático). |
| POST | `/api/v1/models/validate` | Valida un modelo candidato contra el baseline. |
| POST | `/api/v1/models/deploy` | Despliega un modelo validado a producción. |
| POST | `/api/v1/models/rollback` | Revierte al respaldo anterior (o al indicado). |
| GET | `/api/v1/models/history` | Historial de versiones entrenadas. |
| POST | `/api/v1/predict` | Inferencia con el modelo en producción. |
| GET | `/api/v1/status` | Estado general del pipeline. |

Las card views detalladas de parámetros de **entrada** y **salida** de
cada endpoint están documentadas como comentario en la cabecera de
`app.py`.

## Correcciones y decisiones de diseño respecto al stub original

1. **Módulo monolítico → paquete organizado**: el stub original mezclaba
   `KnowledgeBase`, `DataCollector`, `ModelValidator`, DAGs de Airflow,
   `ModelTrainer` y `DeploymentManager` en un único archivo `UC-179.py`
   con comentarios `# core/...`  indicando la estructura deseada pero sin
   implementarla. Se reorganizó en `core/`, `models/`, `workflows/`,
   siguiendo esa misma estructura ya sugerida en el stub.
2. **Métodos faltantes**: `DataCollector.collect_from_sources` invocaba
   `_process_annotations` y `_process_external_data`, que no existían.
   Implementados en `core/data_collector.py`.
3. **Archivo truncado**: `core/deployment_manager.py` (`deploy_model`)
   estaba incompleto (cortado a mitad de una línea). Completado con
   respaldo automático del modelo anterior y método `rollback`.
4. **Encapsulación de acceso a datos rota**: `ModelTrainer._get_active_model`
   accedía a `sqlite3` directamente sin importarlo y sin pasar por
   `KnowledgeBase`. Corregido: `KnowledgeBase` expone
   `get_active_model_path()`/`get_active_model_metrics()`, y
   `ModelTrainer` las consume en vez de SQL directo.
5. **Bug de orden de consultas SQL**: varias consultas usaban
   `ORDER BY timestamp DESC LIMIT 1`, pero `CURRENT_TIMESTAMP` de SQLite
   tiene resolución de 1 segundo — dos registros creados en el mismo
   segundo se desempataban de forma arbitraria. Corregido usando
   `ORDER BY id DESC` (el autoincremento garantiza el orden real de
   inserción).
6. **Inconsistencia semántica del flag `validated`**: `get_new_samples_count`
   contaba filas con `validated=0` como "nuevas", mientras que
   `get_training_data(validated_only=True)` usaba `validated=1` para
   entrenar — es decir, el disparador de reentrenamiento nunca se
   activaría con datos realmente utilizables para entrenar. Se
   redefinió `validated` como "aprobado para entrenamiento" de forma
   consistente en ambos métodos, y se agregó el método/endpoint
   `approve_samples` / `POST /api/v1/data/validate` para exponer ese
   paso de aprobación explícitamente.
7. **Dependencia pesada innecesaria**: la validación lingüística original
   requería `spacy` + descarga del modelo `es_core_news_sm`. Se
   reemplazó por un heurístico ligero (tokenización por regex, ratio de
   mayúsculas) sin dependencias de descarga, manteniendo el mismo
   contrato (`filter_data`).
8. **Sin interfaz HTTP ni orquestador reutilizable**: el stub solo podía
   invocarse importando las clases sueltas. Se creó
   `pipeline_service.ContinuousLearningPipeline` como orquestador único,
   reutilizado por `app.py` (API), `UC-179.py` (CLI) y las DAGs de
   `workflows/` (Airflow), evitando duplicar lógica de negocio entre
   interfaces de entrada.
9. **Sin pruebas**: se agregaron 70 pruebas unitarias y de integración
   (`tests/`) cubriendo `KnowledgeBase`, `DataCollector`,
   `ModelValidator`, `ModelTrainer`, `DeploymentManager`,
   `ContinuousLearningPipeline` y los endpoints de `app.py`.

## Pruebas


`tests/test_knowledge_base.py`, `test_data_collector.py`,
`test_model_validator.py`, `test_trainer.py`, `test_deployment_manager.py`

los 10 endpoints de `app.py`, incluyendo el ciclo
ingesta→validación→entrenamiento→validación→despliegue→predicción→rollback.
