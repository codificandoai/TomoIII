3. Qué tareas realizaría Hugging Face
Inferencia y selección de modelos
UC-317 puede usar Hugging Face para clasificación de sentimiento, extracción de entidades, embeddings, generación de texto, visión, audio, transcripción y modelos multimodales. En trading, por ejemplo, un modelo puede clasificar noticias, extraer eventos corporativos, resumir reportes o producir una señal auxiliar. La señal debe entrar en UC-315 como evidencia con confianza, versión de modelo, timestamp y procedencia; nunca como orden ejecutable.

Evaluación comparativa
UC-315 puede solicitar a UC-317 que ejecute el mismo conjunto de casos contra varios modelos. UC-317 registra latencia, coste, tasa de error, estabilidad, calidad y comportamiento ante entradas adversariales. UC-315 compara los resultados y propone un modelo preferido. UC-324 valida que la evaluación no incluya PII no autorizada, que los modelos estén permitidos y que el modelo seleccionado tenga licencia, Model Card y procedencia verificables.

Entrenamiento y fine-tuning
El entrenamiento debe ejecutarse como un job aislado, reproducible y versionado. Transformers.Trainer ofrece un ciclo de entrenamiento y evaluación configurable con datasets, métricas, callbacks, checkpoints y soporte distribuido/mixed precision 3. UC-315 puede proponer el objetivo de entrenamiento y las métricas, pero UC-317 ejecuta el job y UC-324 verifica el dataset, los permisos, la contaminación de datos, el uso de PII, el presupuesto de cómputo, los resultados y el rollback.

Datasets y memoria de aprendizaje
La librería Datasets permite cargar, procesar y hacer streaming de datasets de audio, visión y NLP, con integración con repositorios del Hub 4. En esta arquitectura, los episodios de UC-315 no deben publicarse automáticamente. Deben pasar por desidentificación, clasificación de sensibilidad, revisión de licencia y validación de calidad. Los datos privados de trading, credenciales, órdenes y resultados de clientes deben permanecer en almacenamiento privado controlado por UC-317.

Registro, trazabilidad y model governance
Cada modelo promovido debe tener un Model Card que documente uso previsto, limitaciones, sesgos, parámetros de entrenamiento, datasets, evaluación, licencia y relación con el modelo base 5. El Hub ofrece repositorios privados, tokens, MFA, grupos de recursos, firmas de commits y escaneos de malware, pickle y secretos 6. Estas funciones mejoran la gobernanza, pero no sustituyen los controles UC-324.

Despliegue
Para producción, Hugging Face Inference Endpoints puede proporcionar infraestructura administrada, autoscaling, observabilidad e integración con vLLM, TGI o contenedores personalizados 7. Para demos internas o validación humana, Spaces puede servir una interfaz Gradio o Docker versionada como repositorio; los secretos deben mantenerse en el mecanismo de secrets, nunca en el código 8. Un Space no debe tener acceso directo a acciones financieras ni a credenciales de corretaje.

5. Ejemplo de adaptador de inferencia en UC-317
El siguiente ejemplo muestra una interfaz mínima. El token debe existir únicamente como secreto del entorno de UC-317. El código no permite que el modelo llame herramientas ni ejecute acciones externas.

# uc317/huggingface_gateway.py
from dataclasses import dataclass
from typing import Any
import os
import time
from huggingface_hub import InferenceClient
 
@dataclass
class ModelResult:
    model_id: str
    provider: str
    text: str
    latency_ms: float
    request_id: str
    confidence: float | None = None
 
class HuggingFaceModelGateway:
    def __init__(self, allowed_models: set[str], allowed_providers: set[str]):
        self.allowed_models = allowed_models
        self.allowed_providers = allowed_providers
        self.client = InferenceClient(token=os.environ["HF_TOKEN"])
 
    def chat(self, *, model_id: str, provider: str, messages: list[dict[str, str]],
             request_id: str, max_tokens: int = 512) -> ModelResult:
        if model_id not in self.allowed_models:
            raise PermissionError("model_not_allowlisted")
        if provider not in self.allowed_providers:
            raise PermissionError("provider_not_allowlisted")
        if any(len(m.get("content", "")) > 12000 for m in messages):
            raise ValueError("input_too_large")
 
        started = time.perf_counter()
        output = self.client.chat.completions.create(
            model=f"{model_id}:{provider}",
            messages=messages,
            max_tokens=max_tokens,
            temperature=0.0,
        )
        latency_ms = (time.perf_counter() - started) * 1000
        text = output.choices[0].message.content or ""
        return ModelResult(
            model_id=model_id,
            provider=provider,
            text=text,
            latency_ms=latency_ms,
            request_id=request_id,
        )

En producción, el gateway debe añadir timeout, circuit breaker, rate limit, redacción PII, hash de entrada, hash de salida, coste estimado, versión de contrato, trazabilidad distribuida y almacenamiento de la respuesta en un audit log. El modelo debe producir datos estructurados, preferentemente JSON validado contra un esquema, en lugar de texto que pueda interpretarse como una orden.

from pydantic import BaseModel, Field
 
class SentimentEvidence(BaseModel):
    label: str = Field(pattern="^(positive|neutral|negative|uncertain)$")
    confidence: float = Field(ge=0.0, le=1.0)
    entities: list[str]
    rationale: str
 
class MarketSentimentSkill:
    action_class = "read"
    risk_level = "low"
    reversible = True
 
    def __init__(self, hf_gateway):
        self.hf = hf_gateway
 
    def run(self, ticker: str, article: str, request_id: str) -> SentimentEvidence:
        result = self.hf.chat(
            model_id="ORG/market-sentiment-model",
            provider="hf-inference",
            request_id=request_id,
            messages=[
                {"role": "system", "content": (
                    "Classify market sentiment. Return JSON only with label, "
                    "confidence, entities and rationale. Do not propose trades."
                )},
                {"role": "user", "content": f"Ticker: {ticker}\nArticle: {article}"},
            ],
        )
        return SentimentEvidence.model_validate_json(result.text)

7. Ejemplo de ejecución paralela de varios modelos
UC-315 puede pedir a UC-317 que compare tres modelos, mientras UC-317 usa su scheduler. El resultado debe ser una evaluación, no una votación automática que ejecute una orden.

# uc315/model_benchmark.py
from concurrent.futures import ThreadPoolExecutor, as_completed
 
MODELS = [
    ("ORG/market-sentiment-small", "hf-inference"),
    ("ORG/market-sentiment-medium", "together"),
    ("ORG/market-sentiment-private", "local-endpoint"),
]
 
def evaluate_one(gateway, model_id, provider, prompt, request_id):
    result = gateway.chat(
        model_id=model_id,
        provider=provider,
        messages=[{"role": "user", "content": prompt}],
        request_id=request_id,
    )
    return {
        "model_id": model_id,
        "provider": provider,
        "text": result.text,
        "latency_ms": result.latency_ms,
    }
 
def benchmark(gateway, prompt, trace_id):
    with ThreadPoolExecutor(max_workers=3) as pool:
        futures = [
            pool.submit(evaluate_one, gateway, model, provider, prompt,
                        f"{trace_id}:{i}")
            for i, (model, provider) in enumerate(MODELS)
        ]
        return [future.result() for future in as_completed(futures)]

UC-324 debe aplicar límites de concurrencia, coste y tiempo; además, debe tratar el resultado de cada modelo como contenido no confiable hasta que el esquema, la procedencia y las reglas de salida hayan sido verificados.

8. Ejemplo de entrenamiento controlado
El entrenamiento debe ser una tarea separada del bucle de ejecución de mercado. No se deben actualizar pesos en línea mientras existe una orden externa pendiente. El patrón seguro es: recopilar episodios, desidentificar, crear dataset versionado, entrenar en sandbox, evaluar, ejecutar red-team, crear checkpoint, solicitar aprobación y promover mediante canary.

# uc317/train_candidate.py
from datasets import load_dataset
from transformers import AutoTokenizer, AutoModelForSequenceClassification
from transformers import Trainer, TrainingArguments
 
BASE_MODEL = "ORG/market-sentiment-base"
DATASET_ID = "ORG/market-sentiment-approved-v3"
OUTPUT_DIR = "artifacts/market-sentiment-candidate-v4"
 
# El dataset debe haber pasado previamente por UC-324: licencia, PII,
# prompt-injection, duplicados, contaminación y trazabilidad.
dataset = load_dataset(DATASET_ID, revision="COMMIT_SHA_PINNED")
tokenizer = AutoTokenizer.from_pretrained(BASE_MODEL, revision="COMMIT_SHA_PINNED")
model = AutoModelForSequenceClassification.from_pretrained(
    BASE_MODEL, revision="COMMIT_SHA_PINNED", num_labels=4
)
 
def tokenize(batch):
    return tokenizer(batch["text"], truncation=True, max_length=512)
 
tokenized = dataset.map(tokenize, batched=True)
args = TrainingArguments(
    output_dir=OUTPUT_DIR,
    eval_strategy="epoch",
    save_strategy="epoch",
    load_best_model_at_end=True,
    metric_for_best_model="eval_f1",
    report_to=[],
)
trainer = Trainer(
    model=model,
    args=args,
    train_dataset=tokenized["train"],
    eval_dataset=tokenized["validation"],
)
trainer.train()
trainer.save_model(OUTPUT_DIR)

9. Cómo debe actuar UC-324 sobre Hugging Face
Gate PRE
Antes de descargar un modelo, dataset o adapter, UC-324 verifica el repositorio allowlisted, propietario, revisión fijada por commit, licencia, Model Card, escaneos, tamaño, formato, dependencias y riesgo de ejecución de código. Para inferencia valida token, proveedor, modelo, coste, latencia, PII, prompt injection y límite de concurrencia. Para entrenamiento valida dataset, procedencia, licencia, separación train/validation/test, contaminación y presupuesto.

Gate EXEC
La solicitud de UC-317 debe estar firmada con intención, nonce, timestamp y TTL. Para una llamada de solo lectura al modelo, el riesgo puede ser bajo; para publicar un modelo, crear un endpoint, cambiar visibilidad, lanzar un job costoso o promover un checkpoint, el riesgo aumenta y requiere una política más estricta. El modelo nunca recibe el secreto HMAC ni las credenciales de acciones externas.

Gate POST
Después de la inferencia, UC-324 valida el esquema de salida, presencia de contenido prohibido, fuga de PII, instrucciones de uso de herramientas, cambio de formato, score de confianza y consistencia con la tarea. Después del entrenamiento valida métricas, regresiones, comportamiento adversarial, licencia, reproducibilidad, hashes y Model Card. Una violación crítica produce BLOCK, SAFE HOLD o ROLLBACK.

# UTRON.ai centralizando plantillas
---------------------------------
Integración de Hugging Face en UTRON.ai
Por qué vale la pena
Para UTRON.ai, Hugging Face puede funcionar como un catálogo centralizado y versionado de modelos, datasets, adapters, endpoints y demostraciones, sobre el cual se construye una fábrica de plantillas de productos de IA para terceros. El valor no está solamente en tener muchos modelos disponibles, sino en poder estandarizar el ciclo completo: descubrir un modelo, probarlo, compararlo con alternativas, encapsularlo detrás de una API propia, documentar su licencia y limitaciones, desplegarlo de forma administrada o local, y sustituirlo sin rediseñar toda la aplicación.

La integración también reduce el acoplamiento tecnológico. UTRON.ai puede ofrecer una misma plantilla de producto —por ejemplo, un asistente documental— y cambiar entre modelos según coste, latencia, idioma, privacidad, hardware o licencia. Los Inference Providers de Hugging Face proporcionan una interfaz unificada para acceder a modelos mediante distintos proveedores y permiten políticas de selección como fastest, cheapest, preferred o un proveedor explícito 1. InferenceClient también admite modelos del Hub, endpoints dedicados y servidores locales como vLLM, TGI, Ollama o llama.cpp 2.

La integración debe conservar una frontera de gobernanza: UTRON.ai decide qué producto ofrece y con qué reglas; el modelo genera predicciones o contenido; la capa de producto valida la salida; y las acciones sensibles requieren permisos, auditoría y aprobación. Una etiqueta de confianza del modelo nunca debe convertirse automáticamente en una transacción, una modificación de infraestructura o una decisión crítica.

Ejemplo de plantilla UTRON.ai: asistente documental RAG
El producto puede componerse con BAAI/bge-m3 para embeddings, BAAI/bge-reranker-v2-m3 para reordenar resultados y un LLM como Qwen3-8B para redactar la respuesta. UC-317 gestiona la ingestión y el vector store; UC-315 decide cómo descomponer la consulta y qué contexto necesita; UC-324 valida PII, procedencia de documentos, prompt injection y salida. El cliente recibe una API con autenticación, citas, historial, panel de evaluación y configuración de modelos sin tener que construir el pipeline desde cero.

Ejemplo de plantilla UTRON.ai: inteligencia financiera
El producto puede usar FinBERT para clasificar sentimiento financiero, Whisper para transcribir reuniones o llamadas de analistas y BGE-M3 para recuperar reportes históricos. UC-315 integra las evidencias con precios y memoria de dominio; UC-317 ejecuta los modelos y almacena resultados; UC-324 evita que una señal textual se convierta directamente en una orden. Las salidas comerciales recomendadas son alertas, dashboards, investigación asistida, análisis de riesgo y generación de informes.

Ejemplo de plantilla UTRON.ai: contact center
Whisper transcribe, un embedding model recupera políticas, un reranker selecciona los fragmentos relevantes y un LLM redacta una respuesta sugerida. Un clasificador zero-shot puede enrutar el caso a facturación, soporte, cancelación o escalamiento. El agente humano aprueba las respuestas sensibles y todas las interacciones quedan auditadas. Esta composición es más vendible que ofrecer un modelo aislado porque entrega un flujo operativo completo.

Ejemplo de plantilla UTRON.ai: procesamiento documental
TrOCR puede extraer texto manuscrito, un modelo de clasificación puede identificar el tipo de documento, BGE-M3 puede indexarlo y un LLM puede generar una ficha estructurada. La plantilla debe incluir validación de campos, confianza mínima, revisión humana, protección de PII y almacenamiento por tenant. La propuesta de valor es convertir documentos desordenados en datos verificables y conectarlos con sistemas empresariales.

Cómo convertir modelos en productos repetibles
UTRON.ai debe empaquetar cada solución en cinco artefactos: un Model Manifest con IDs y revisiones fijadas; un Skill Contract con entradas, salidas, permisos y riesgo; un Evaluation Pack con casos normales y adversariales; un Deployment Profile para local, Provider o Endpoint; y un Product Config con tenant, idioma, límites, branding, retención y conectores. Así, el modelo se convierte en un componente sustituible dentro de una plantilla comercial, no en una dependencia rígida.

El registro de cada modelo debe conservar el commit o revisión exacta, licencia, Model Card, dataset, métrica, hardware recomendado, coste estimado, latencia, limitaciones y fecha de aprobación. La plataforma de Hugging Face ofrece mecanismos de seguridad como repositorios privados, tokens, MFA, resource groups, commit signatures, malware scanning, pickle scanning y secrets scanning 6, pero UTRON.ai debe mantener además su propia allowlist, auditoría, aislamiento por cliente y control de acciones.

Conclusión
La integración UTRON.ai utiliza para construir plantillas completas, intercambiables y gobernadas, no simplemente para revender acceso a modelos. La ventaja competitiva estará en la capa de producto: orquestación, memoria, evaluación, seguridad, personalización por cliente, observabilidad y despliegue. Hugging Face aporta el ecosistema centralizado de modelos y herramientas; UTRON.ai debe aportar el empaquetado comercial, la integración con procesos reales y la gobernanza que transforma modelos abiertos en soluciones empresariales confiables.

## 15. Documentación completa de integración UC-320

Esta sección explica de forma exhaustiva cómo funciona UC-320 y cómo se
integra con UC-315, UC-317, UC-324 y Hugging Face. Está pensada para
equipos de integración, arquitectos y desarrolladores que necesiten
conectar soluciones AI-native con el ecosistema.

### 15.1. Qué es UC-320

UC-320 es la **capa de integración de Hugging Face** que conecta el
ecosistema de modelos abiertos (Hub, Inference Providers, Endpoints,
Datasets, Transformers, PEFT, Evaluate, Spaces) con los tres sistemas
nucleares de Codificando.AI:

| Sistema | Rol en la integración UC-320 |
|---|---|
| **UC-315** | Cerebro AGI que decide qué modelo usar, formula hipótesis, interpreta evidencia y propone acciones de dominio. |
| **UC-317** | Kernel AIOS-style que proporciona infraestructura de ejecución (LLM Core, Tools, Memory, Storage, Scheduler). |
| **UC-324** | Protocolo de contención que valida, audita y bloquea acciones con gates PRE/EXEC/POST. |
| **Hugging Face** | Catálogo de modelos, datasets, inferencia, entrenamiento y despliegue. |
| **UC-320** | Adaptador que orquesta todo: gateway de modelos, skills, benchmark, training, gates, contracts y templates. |

**UC-320 no es un cuarto cerebro.** Es un puente gobernado que permite
usar Hugging Face sin acoplar el sistema a un proveedor, sin que un
modelo se convierta en autoridad de seguridad, y sin que una salida
generada se transforme automáticamente en una acción externa.

### 15.2. Reglas de frontera

| Regla | Descripción |
|---|---|
| **R1** | Ningún modelo de HF puede autorizar una compra, venta, pago, reserva o cambio de infraestructura. |
| **R2** | Toda inferencia pasa por UC-324 gates antes de que su resultado sea aceptado como evidencia. |
| **R3** | Toda promoción de modelo requiere aprobación humana + UC-324 gates + red-team. |
| **R4** | Los tokens de HF viven solo en el entorno de UC-320/UC-317, nunca en UC-315 ni en el modelo. |
| **R5** | Los datasets privados (trading, clientes, credenciales) no se publican al Hub sin desidentificación + licencia + UC-324. |
| **R6** | El modelo nunca recibe el secreto HMAC ni credenciales de acciones externas. |
| **R7** | Una confianza de 0.92 del modelo NO es autorización para operar; es solo una variable de entrada. |
| **R8** | UC-320 es fail-closed: si los gates no pueden evaluar, la operación se bloquea. |

```python
import requests

UC320_BASE = "http://localhost:5320"
```

### 15.7. Integración UC-320 ↔ UC-324

UC-324 es el **protocolo de contención** que valida todas las
operaciones. UC-320 implementa una **integración nativa** de los gates
de UC-324 en `uc324_gates.py`, pero en producción debe delegar al API
REST de UC-324.

| Gate | Cuándo se ejecuta en UC-320 | Qué valida |
|---|---|---|
| PRE | Antes de inferencia | Allowlist, PII, prompt injection, cost, latency. |
| EXEC | Durante inferencia | HMAC, nonce, anti-replay, anti shell/SQL. |
| POST | Después de inferencia | Output no vacío, sin tool instructions, sin PII leaked. |

**Dos modos de integración:**

1. **Modo nativo (default):** UC-320 usa `uc324_gates.py` que replica
   los gates A-K deterministamente. Útil para tests y desarrollo.

2. **Modo delegado (producción):** UC-320 hace HTTP POST al API de
   UC-324 (`http://localhost:5324/api/v1/containment/check`) para cada
   operación. UC-324 ejecuta sus gates completos con adapters A-K.

```python
# Modo delegado (producción):
import requests

UC324_BASE = "http://localhost:5324"


def uc324_validate(contract: dict) -> dict:
    """UC-320 delega validación a UC-324."""
    resp = requests.post(f"{UC324_BASE}/api/v1/containment/check", json=contract)
    return resp.json()  # {"allowed": bool, "issues": [...], "audit_log": [...]}
```

### 15.8. Integración UC-320 ↔ Hugging Face

UC-320 usa Hugging Face a través del `HuggingFaceModelGateway` que
abstrae `huggingface_hub.InferenceClient`.

| Capacidad HF | Cómo la usa UC-320 | Requiere |
|---|---|---|
| Inference Providers | `HuggingFaceBackend.chat()` | `HF_TOKEN` + `huggingface_hub` |
| Inference Endpoints | Configurable via `base_url` | Endpoint dedicado |
| Datasets | `TrainingManager` (stub) | `datasets` lib |

| Model Cards | `TrainingJob.model_card` | Generado automáticamente |

**Backend mock vs HuggingFace:**

| Aspecto | Mock | HuggingFace |
|---|---|---|

### 15.9. SecureContract — El contrato entre los cuatro

Toda operación entre UC-315, UC-317, UC-324 y Hugging Face se formaliza
con un `SecureContract`:

```json
{
  "request_id": "trace-2026-001",
  "caller": "UC-315",
  "executor": "UC-317",
  "guard": "UC-324",
  "operation": "model_inference",
  "domain": "trading",
  "model_id": "ProsusAI/finbert",
  "model_revision": "COMMIT_SHA_PINNED",
  "provider": "hf-inference",
  "input_class": "market_news_public",
  "action_class": "read",
  "risk_level": "low",
  "max_cost": 0.05,
  "max_latency_ms": 3000,
  "output_schema": "SentimentEvidence.v1",
  "allow_tools": false,
  "requires_human_approval": false,
  "audit_required": true,
  "nonce": "unique_nonce_abc123",
  "timestamp": 1234567890,
  "input": {
    "ticker": "AAPL",
    "article": "Apple beats earnings expectations by 15%"
  }
}
```

**Reglas del contrato:**

| Campo | Regla |
|---|---|
| `allow_tools` | Siempre `false` para inferencia. El modelo no llama tools. |
| `requires_human_approval` | `false` para `read`; `true` para `execute`, `delete`, `promote`. |
| `action_class` | `read` = solo lectura; `execute` = tiene efectos; `delete` = irreversible. |
| `risk_level` | `low` < `medium` < `high` < `critical`. UC-324 valida según rol. |
| `nonce` | Único por operación. Anti-replay. |
| `output_schema` | Define el schema esperado. UC-324 Gate POST valida. |

```text
UC-315  = CEREBRO       → "sé qué modelo necesito y qué hacer con la evidencia"

UC-324  = SUPERVISOR    → "sé qué bloquear antes de que tenga efectos reales"

UC-320 integra todo:

  - Benchmark paralelo para evaluar modelos
  - Training controlado con promoción humana
  - Gates PRE/EXEC/POST de UC-324 en cada operación
  - SecureContract entre los cuatro sistemas
  - 6 plantillas UTRON.ai listas para comercializar

Regla de oro:
  "Un modelo genera evidencia. La evidencia no es una orden.
   La orden requiere UC-315 + UC-324 + (a veces) humano."
```
