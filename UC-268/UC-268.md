## Descripción

UC-268 implementa un **protocolo de comunicación segura entre agentes** para Mustiamente, basado en **A2A (Agent2Agent)** de Google. Mientras que MCP conecta agentes con herramientas y datos, **A2A conecta agentes con otros agentes**, permitiendo orquestación distribuida, descubrimiento de capacidades y delegación de tareas.

El enfoque sigue los principios de **A2A enterprise-ready**:

- **Transporte seguro**: HTTPS/TLS 1.2+ en producción.
- **Sin identidad en el payload**: la autenticación ocurre en la capa HTTP.
- **Autenticación**: OAuth2 / OpenID Connect Bearer tokens y API keys.
- **Autorización**: roles y scopes por skill, respondiendo `401` o `403` según corresponda.
- **Agent Card**: cada agente publica su tarjeta (`/.well-known/agent.json`) con capacidades y esquemas de seguridad soportados.
- **JSON-RPC 2.0**: mensajes `tasks/send`, `tasks/get`, `tasks/cancel` sobre HTTPS.

Además, el sistema interno de Mustiamente mantiene:

- **Envelope con trazabilidad**: `message_id`, `correlation_id`, `causation_id`, `trace_id`, `ttl_ms`, `priority`.
- **Pydantic en bordes**: validación estricta de payloads de red.
- **Dataclasses con slots** para comunicación in-process de alto rendimiento.
- **Bus de mensajes interno** con interceptores, TTL y métricas.

## 1. Arquitectura A2A

```mermaid
graph TD
    A[Cliente / Otro agente] -->|HTTPS + Bearer/API key| B[A2A Server Flask]
    B --> C[/.well-known/agent.json]
    B --> D[/a2a JSON-RPC]
    D --> E[Task Handler]
    E --> F[MessageBus interno]
    F --> G[PlannerAgent]
    F --> H[SimulatorAgent]
    F --> I[CriticAgent]
    F --> J[ExecutorAgent]
    F --> K[UserProxyAgent]
    G --> L[(SQLite/vector store opcional)]
    B --> M[SecurityManager OAuth2/API key/scopes]
```

### Roles de agentes

| Agente | Rol A2A | Responsabilidad |
|---|---|---|
| `PlannerAgent` | Cliente + servidor | Recibe búsquedas, orquesta simulación/crítica/ejecución. |
| `SimulatorAgent` | Servidor especializado | Simula planes con Monte Carlo. |
| `CriticAgent` | Servidor especializado | Evalúa planes simulados y emite veredicto. |
| `ExecutorAgent` | Servidor especializado | Simula reservas y reporta ejecución. |
| `UserProxyAgent` | Cliente | Inicia flujos y recibe resultados. |

## 2. Seguridad (enterprise-ready)

### Capa de transporte

```text
Recomendación: HTTPS obligatorio, TLS 1.2+, verificación de certificados.
Variable UC268_REQUIRE_TLS: true/false
```

### Autenticación

| Mecanismo | Header | Implementación |
|---|---|---|
| Bearer (JWT) | `Authorization: Bearer <token>` | PyJWT con secret configurable. |
| API key | `X-API-Key: <key>` | Lista de keys permitidas. |

### Autorización

Cada skill en el Agent Card declara los scopes requeridos. El `SecurityManager` verifica que el token/API key tenga al menos uno de esos scopes. El scope `admin` otorga todos los permisos.

```python
# Decorador Flask
@require_auth(scopes=["a2a:write"])
def a2a_jsonrpc():
    ...
```

### Respuestas de error

- `401 Unauthorized`: credenciales faltantes o inválidas, con `WWW-Authenticate: Bearer realm="a2a"`.
- `403 Forbidden`: credenciales válidas pero sin scope para la skill.

## 4. Flujo interno del bus de mensajes

```text
UserProxyAgent
    │
    ▼ flight.search_request
PlannerAgent
    │
    ├─► flight.search_response ─► UserProxyAgent
    │
    ▼ plan.simulate_request
SimulatorAgent
    │
    ▼ plan.simulate_response
CriticAgent
    │
    ▼ plan.critique_response
PlannerAgent
    │
    ├─ approved ─► ExecutorAgent ─► plan.execution_report
    └─ needs_revision ─► replanificar
```

Cada mensaje lleva:

- `correlation_id`: agrupa toda la tarea.
- `causation_id`: id del mensaje que lo causó.
- `message_id`: id único.
- `ttl_ms`: expiración automática.

## 10. Comparación: Pydantic vs Dataclass

| Aspecto | Pydantic | Dataclass |
|---|---|---|
| **Dónde se usa** | Bordes (API, red, colas) | Interno (in-process) |
| **Validación** | Automática y estricta | Ninguna (confianza) |
| **Serialización** | JSON nativo (`model_dump_json`) | Manual (`asdict` + json) |
| **Velocidad** | ~5-10μs por validación | ~0.1μs (casi gratis) |
| **Inmutabilidad** | `frozen=True` | `frozen=True` + `slots=True` |
| **Tipado** | Coerción automática | Estricto sin coerción |
| **Uso de memoria** | Mayor (overhead validación) | Mínimo con `slots=True` |

**Regla de oro en Mustiamente:**

```text
BORDES (API, red, colas)      →  PYDANTIC
INTERNO (agentes in-process)  →  DATACLASS con slots
CONVERSIÓN                    →  .from_pydantic() / .to_pydantic()
```

## 11. Limitaciones y próximos pasos

- El cliente A2A actual usa `urllib` para demostración; producción puede usar `httpx` con certificados TLS, retries y conexión persistente.
- Las tareas se procesan de forma síncrona en el servidor; tareas largas deberían usar `tasks/sendSubscribe` con push notifications o WebSockets.
- El bus interno es síncrono; para alta concurrencia se puede reemplazar por `asyncio` + `asyncio.Queue` o un broker real (Redis, RabbitMQ).
- La persistencia de tareas y mensajes puede integrarse con SQLite/PostgreSQL y vector store.
- Los scopes actuales son estáticos; producción debería consultar un identity provider (IdP) para obtener roles reales.
