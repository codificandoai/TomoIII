# TomoIII
## AI-Native Operations &amp; Agentic Patterns
### CASE: UC-308 — SANIDAD DEL ECOSISTEMA AGI: Agent Drift / Environmental Degradation

**Uso:** INTERNO  
**Versión:** 1.0.0  
**Ambito:** capa externa de evaluación continua. No forma parte de UC-315, no ejecuta agentes reales y **nunca** modifica automáticamente código, prompts, políticas o selectores.

---

## 1. Resumen

UC-308 implementa un **pipeline de evaluación continua nocturna (Nightly Regression Testing)** orientado a detectar la **deriva del agente** y la **degradación del entorno**. El principio central es:

> El código del agente permanece estático, pero el mundo exterior cambia: una API modifica su contrato JSON, un sitio web actualiza sus clases CSS, la distribución de datos subyacente muta, las herramientas se vuelven más lentas o empiezan a devolver errores, y el comportamiento del agente (pasos, reintentos, escalaciones) se desvía.

Para combatir esto, UC-308 mantiene un **Golden Dataset versionado y firmado**, ejecuta el mismo conjunto de tareas periódicamente, compara los resultados contra **baselines por agente/herramienta/entorno/versión** y emite alertas con recomendaciones de mitigación. Todo corre en un **sandbox simulado**: sin red, sin APIs reales, sin archivos reales y sin side effects.

## 2. Alcance

### Dentro del alcance
- Detección de seis tipos de deriva:
  1. **Contract/API schema drift**
  2. **HTML / interface drift**
  3. **Data distribution drift** (PSI / z-score / divergencia)
  4. **Tool operational drift** (latencia, errores, timeouts, recursos)
  5. **Behavioral drift** (pasos, reintentos, escalaciones, bloques UC-300, overrides UC-290)
  6. **Quality drift** (tasa de éxito, quality score)
- Golden dataset versionado, hasheado y firmado (HMAC-SHA256).
- Casos públicos y secretos (metadatos de secretos expuestos sin payload).
- Baselines versionados por `(agent_id, tool, environment, agent_version)`.
- Comparación absoluta y relativa contra baseline.
- Estados `normal / warning / degraded / critical`.
- Ventanas móviles e histéresis (consecutive failures) para evitar fatiga de alertas.
- Recomendaciones: alertar, incrementar HITL (UC-290), deshabilitar tool (UC-300), contención/rollback (UC-324). **Ninguna** es auto-aplicada.
- Scheduling configurable (cron de 5 campos) y event-triggered.
- API REST Flask con INPUT/OUTPUT cards, health, schema, run-evaluation, baselines, datasets, history, alerts, status, metrics, reset.
- Exportador Prometheus propio (sin dependencia obligatoria de `prometheus_client`) con labels seguras.
- CLI (`UC-308.py`) con subcomandos `api`, `run`, `demo`, `validate`.
- Validador y suite de tests pytest.
- Artefactos PromQL, Prometheus, Grafana y Alertmanager.

### Fuera del alcance
- No ejecuta agentes reales ni LLMs.
- No realiza llamadas de red, escrituras de archivo ni mutaciones de estado externos.
- No modifica automáticamente código, prompts, policies ni selectores HTML.
- No sustituye a UC-315 (observabilidad interna) ni a UC-290/300/324; los consume conceptualmente vía telemetría.

## 4. Macroproceso

1. **Inicializar Golden Dataset**  
   Cargar casos públicos y secretos, verificar hash y firma.
2. **Establecer Baselines**  
   Ejecutar una corrida "healthy" y grabar métricas por `(agent, tool, env, version)`.
3. **Evaluación continua**  
   Ejecutar el golden dataset periódicamente (nightly y/o por evento).
4. **Detección de deriva**  
   Cada detector compara la corrida actual contra el baseline.
5. **Agregación de estado**  
   Se asigna `normal / warning / degraded / critical`.
6. **Supresión y resolución por histéresis**  
   Solo se alerta cuando una condición se sostiene `N` corridas consecutivas; dos corridas normales consecutivas resuelven las alertas activas sin eliminar su historial ni marcarlas como reconocidas por un humano.
7. **Recomendación**  
   El `MitigationAdvisor` sugiere acciones humanas.
8. **Revisión / contención**  
   Operador humano decide aplicar cambios (UC-290, UC-300, UC-324).

## 5. Subprocesos

### 5.1 Golden Dataset
- Casos `GoldenCase` con `id`, `tool`, `environment`, `input_payload`, `expected_schema_keys`, `expected_html_selectors`, `expected_output`, `distribution_config` y flag `secret`.
- `GoldenDataset.compute_hash()` genera SHA-256 del contenido canónico.
- `GoldenDataset.sign(secret_key)` produce HMAC-SHA256.
- `verify_signature` e `verify_integrity` detectan cualquier manipulación.

### 5.2 Sandbox de entorno
- `SimulatedExternalEnvironment` no toca red, APIs ni archivos.
- Cada caso se ejecuta con un RNG determinista derivado del caso + escenario, garantizando reproducibilidad en latencia, tokens y recursos.
- Escenarios soportados: `healthy`, `api_schema_change`, `html_selector_change`, `data_distribution_shift`, `latency_regression`, `error_regression`, `timeout_regression`, `behavioral_regression`, `quality_regression`.

### 5.3 Detectores

| Detector | Entrada | Comparación | Salida |
|---|---|---|---|
| `QualityDriftDetector` | success_rate, quality_score | absoluta/relativa vs baseline | `quality` |
| `ToolOperationalDriftDetector` | latencia p95/media, error_rate, timeout_rate, recursos | absoluta/relativa | `tool_operational` |
| `APIContractDriftDetector` | schema_fingerprint | conjunto de keys esperado vs actual | `contract_api` |
| `HTMLInterfaceDriftDetector` | html_fingerprint (selectores) | selectores esperados vs actual | `html_interface` |
| `DataDistributionDriftDetector` | muestras numéricas / conteos categóricos | PSI + z-score de media | `data_distribution` |
| `BehavioralDriftDetector` | steps, retries, escalations, uc300_blocks, uc290_overrides | absoluta/relativa | `behavioral` |

### 5.4 Alert Manager
- Mantiene historial de estados en ventana móvil.
- Configuración: `consecutive_degraded_to_alert`, `consecutive_critical_to_alert`.
- Emite alertas en memoria; no hay webhooks/email salientes.
- Soporta `acknowledge(alert_id)`.

### 5.5 Recomendaciones
| Estado / deriva | Recomendación |
|---|---|
| Cualquiera | `alert_team` |
| `contract_api` degraded/critical | `disable_tool_uc300` |
| `html_interface` degraded/critical | `disable_tool_uc300` |
| `quality/behavioral/operational` degraded/critical | `increase_hitl_uc290` |
| `critical` global | `containment_rollback_uc324` |

Todas tienen `auto_apply=false`.

## 6. Threat model

| Amenaza | Mitigación en UC-308 |
|---|---|
| Falsos positivos por ruido | Ventanas móviles, histéresis, umbrales absolutos + relativos |
| Fatiga de alertas | Estado agregado + alerta solo tras N corridas consecutivas |
| Golden dataset alterado | Hash SHA-256 + firma HMAC; validación en carga |
| Auto-modificación peligrosa | Diseño read-only: nunca muta código/prompts/policies/selectors |
| Side effects externos | Sandbox simulado; sin red, APIs ni archivos reales |
| Fuga de casos secretos | API `/datasets` omite payloads de casos secretos por defecto |
| Dependencias pesadas | stdlib + Flask + pytest; exportador Prometheus propio |

## 7. Diferencias: UC-162 conceptual vs UC-308 operational

| Aspecto | UC-162 | UC-308 |
|---|---|---|
| Enfoque | Drift conceptual/semántico del corpus LLM | Degradación operacional del agente en su entorno |
| Entradas | Documentos, respuestas LLM, prompts | Golden dataset de tareas y telemetría de ejecución |
| Detectores | Bias, hallucination, concept drift | Contract, HTML, data, operational, behavioral, quality |
| Baselines | Conceptos y embeddings | Métricas por agente/tool/env/version |
| Acciones | Registro de linaje, aprobación de prompts | Recomendaciones HITL/disable/containment (no auto-mod) |
| Relación | Fuente conceptual de telemetría | Consumidor operacional de UC-162/083/290/300/315/324 |

## 11. Scheduling cron / nightly

`nightly_scheduler.py` implementa un parser cron de 5 campos en UTC:

```python
NightlyScheduler("0 2 * * *")   # 02:00 UTC todos los días
```

- `is_due(now)` evita ejecutar más de una vez por minuto.
- `run_now()` / `trigger_event()` para ejecución manual o por evento.
- El orquestador expone `run_if_due(now)`.

Ejemplo de integración con cron real:

```cron
0 2 * * * cd /ruta/UC-308/code && python UC-308.py run --scenario healthy
```

## 14. Control, contingencia y trazabilidad

- **Evidencia reproducible**: cada `EvaluationRun` guarda `seed`, escenario, versión del dataset y hash.
- **Dataset firmado**: cualquier manipulación del golden dataset rompe `verify_integrity()` / `verify_signature()`.
- **Baselines versionados**: se identifican por `baseline_id` y clave compuesta.
- **Alertas trazables**: cada alerta vincula `run_id` y `drift_signal_ids`.
- **Logs estructurados**: `ObservabilityManager` almacena logs, trazas y métricas en memoria.
- **Contingencia**: en estado `critical` se recomienda contención/rollback vía UC-324; en deriva de API/HTML se recomienda deshabilitar la herramienta en UC-300 hasta revisión humana.
- **Sin auto-modificación**: todas las recomendaciones requieren aprobación humana (HITL/UC-290).

---

## 15. Nota de simulación y ausencia de side effects

Todo el pipeline de UC-308 es **simulado**:

- No hay sockets salientes.
- No se leen ni escriben archivos reales del entorno (salvo los propios del repositorio).
- No se ejecutan APIs ni bases de datos reales.
- Las métricas Prometheus se generan como texto en memoria; no se abre un servidor pushgateway real.
- El Alertmanager, Prometheus y Grafana son artefactos de configuración/documentación; no se despliegan servicios.

Esto garantiza que UC-308 pueda validarse en cualquier entorno sin riesgo de modificar sistemas productivos.
