Para construir este sistema, debemos implementar el patrón **Human-in-the-Loop (HITL) con Razonamiento Transparente**. La clave arquitectónica es que la IA no toma la decisión de ejecución; construye un " Expediente de Decisión " que incluye los datos procesados, el razonamiento paso a paso y una sugerencia. Si el riesgo es alto o la confianza es baja, se activa un **Punto de Escalamiento** obligando a la intervención humana.

Aquí tienes el algoritmo en Python que implementa esta dinámica exacta.

### Código: Arquitectura Asesor de Trading (Human-in-the-Loop)
### Cómo esta arquitectura resuelve el problema:

1. **Memoria Compartida (`SharedTradingMemory`):**
   Ni la IA ni el Humano tienen estados ocultos. Existe un único objeto `memory` que la IA llena con inferencias (medias móviles, volumen) y el Humano llena con decisiones finales. Si hay un error, se rastrea exactamente qué vio cada uno en ese `tick`.

2. **Razonamiento Transparente (`ai_reasoning_steps`):**
   La IA no devuelve un "Black Box" que diga "Comprar". Devuelve una lista auditada:
   * *Paso 1: Tendencia (Precio > MA20)*
   * *Paso 2: Volumen (Alto, confirma)*
   * *Paso 3: Proyección matemática*
   Esto permite al Humano decir: *"La IA dice Bull porque el volumen es alto, pero yo sé que ese volumen es falso por un split de acciones, voy a hacer override a Bear"*.

3. **Puntos de Escalamiento (`requires_escalation`):**
   Evita la sobredelegación. Si la IA calcula que el movimiento proyectado es mayor al 5% (Riesgo de Flash Crash), o si su confianza interna cae debajo del 65%, **se bloquea a sí misma**. Cambia su sugerencia a `ESCALATE` y dispara una alarma roja, obligando al humano a tomar el mando.

4. **La División del Trabajo:**
   * **La IA (El Analista Operativo):** Hace las matemáticas rápidas, lee las APIs de precios, calcula desviaciones estándar, actualiza medias. Cosas que a un humano le tomaría horas y donde los humanos cometen errores.
   * **El Humano (El Director de Estrategia):** No mira miles de filas de datos. Mira el resumen ejecutivo de la IA y aplica contexto macroeconómico, noticias geopolíticas o intuición (ej. presionar "B" o "E").

Al final, la tabla **"AUDITORÍA DE RENDIMIENTO HITL"** demuestra el valor real: muestra en qué porcentaje el humano estuvo de acuerdo con la máquina (automatización exitosa) y en qué porcentaje el humano hizo un **Override** (aportación de experiencia que la IA no podía tener).

# Implementación UC-290 — HITL con Razonamiento Transparente

![Arquitectura](./uc-290-brain.png)


## 1. Alcance y objetivo

UC-290 es la capa **Human-in-the-Loop (HITL)** que se interpone entre UC-315 (decide) y UC-317 (ejecuta). La IA no toma la decisión de ejecución; construye un **Expediente de Decisión** que incluye datos procesados, razonamiento paso a paso y una sugerencia. Si el riesgo es alto o la confianza es baja, se activa un **Punto de Escalamiento** obligando a intervención humana.

### Bases técnicas

1. **El principio "evidencia no es orden" se aplica también a UC-315**: UC-315 genera una decisión → esa decisión es evidencia de intención, no una orden de ejecución → un humano debe aprobarla cuando el riesgo lo exige.
2. **UC-324 es reactivo, no deliberativo**: UC-324 bloquea por reglas. HITL con razonamiento transparente llena el vacío de decisiones éticamente problemáticas o en zonas grises.
3. **El Expediente de Decisión es el consumidor natural de UC-325**: UC-325 hace auto-reflexión interna y efímera. El Expediente la hace persistente y auditable.
4. **Cumple requisitos regulatorios**: EU AI Act, NIST AI RMF, ISO/IEC 23894 requieren supervisión humana.
5. **Previene el escenario de "rebelión"**: Si UC-315 puede decidir y ejecutar sin checkpoint humano, el sistema permite el escenario que intenta prevenir. HITL es la garantía de que ninguna acción de alto riesgo se ejecuta sin aprobación externa.

### Tipo de agente: Híbrido

- **Reactivo**: deja pasar decisiones de bajo riesgo automáticamente (fast path).
- **Deliberativo**: construye el Expediente de Decisión con razonamiento completo para decisiones de alto riesgo (slow path).

## 4. Subprocesos

### SP-290-01: Evaluación de riesgo

1. Recibir DecisionInput con datos de UC-315 y validaciones externas.
2. Evaluar 7 factores: confianza IA, UC-087, UC-162, UC-325, UC-322, volatilidad, complejidad.
3. Calcular risk_score (0-1) y confidence_score (0-1).
4. Clasificar nivel: none, low, medium, high, critical.
5. Determinar requires_escalation basado en umbrales configurables.

### SP-290-02: Construcción del expediente

1. Crear DecisionDossier con ID único.
2. Consolidar pasos de razonamiento de UC-315, UC-087, UC-162, UC-325, UC-322, UC-329.
3. Agregar paso de evaluación de riesgo.
4. Agregar paso de sugerencia final.
5. Determinar estado: AUTO_EXECUTED o PENDING_REVIEW.
6. Calcular hash SHA-256 del contenido.

### SP-290-03: Escalamiento

1. Si requires_escalation → activar punto de escalamiento.
2. Cambiar estado del expediente a PENDING_REVIEW.
3. Registrar en cola de revisiones pendientes.
4. Notificar al revisor humano (Slack/Teams/webhook).
5. Establecer timeout de escalamiento.

### SP-290-04: Revisión humana

1. Revisor recibe el expediente con razonamiento transparente.
2. Revisor puede: approve, modify, reject, request_more_info, delegate.
3. Registrar acción, razón y notas.
4. Actualizar estado del expediente.
5. Recalcular hash de integridad.

### SP-290-05: Bloqueos duros

1. Si UC-087 rechazó integridad → bloqueo automático.
2. Si UC-162 rechazó LLMOps → bloqueo automático.
3. Si riesgo crítico y require_human_for_critical → bloqueo.
4. Registrar bloqueo en auditoría.

## 6. Configuración

| Parámetro | Default | Descripción |
|-----------|---------|-------------|
| `confidence_threshold` | 0.65 | Confianza mínima para auto-execute |
| `risk_high_threshold` | 0.70 | Score de riesgo para nivel HIGH |
| `risk_critical_threshold` | 0.90 | Score de riesgo para nivel CRITICAL |
| `volatility_threshold` | 0.05 | Volatilidad máxima (5%) |
| `escalation_timeout_sec` | 3600 | Timeout de revisión humana (1 hora) |
| `auto_execute_max_risk` | 0.30 | Riesgo máximo para auto-execute |
| `require_human_for_critical` | True | Requerir humano para riesgo crítico |
| `require_human_for_high_risk` | True | Requerir humano para riesgo alto |
| `allow_auto_execute_low_risk` | True | Permitir auto-execute para riesgo bajo |
| `max_auto_confidence` | 0.85 | Confianza máxima para auto-execute sin humano |

## 10. Trail de auditoría

### Características

- **Hash encadenado**: cada entrada incluye el hash de la anterior (estilo blockchain).
- **Tamper detection**: `verify_chain()` detecta si una entrada fue manipulada.
- **Eventos registrados**: dossier_created, auto_execute, escalation_activated, human_review, decision_blocked, escalation_timeout.
- **Actores**: system, human.
- **Filtrable**: por dossier_id o trace_id.

### Eventos

| Evento | Actor | Descripción |
|--------|-------|-------------|
| `dossier_created` | system | Expediente creado |
| `auto_execute` | system | Auto-ejecución aprobada (fast path) |
| `escalation_activated` | system | Punto de escalamiento activado |
| `human_review` | human | Revisión humana registrada |
| `decision_blocked` | system | Decisión bloqueada por validación fallida |
| `escalation_timeout` | system | Escalamiento expiró sin revisión |

## 11. Integración con el ecosistema

### Boundary

| Capa | Rol | Relación con UC-290 |
|------|-----|---------------------|
| UC-315 | Decide (BDI) | Produce la decisión que UC-290 revisa |
| UC-317 | Ejecuta (reactivo) | Solo ejecuta si UC-290 lo permite |
| UC-324 | Contiene (reactivo) | Bloquea después si algo falla |
| UC-087 | Valida integridad (reactivo) | Input para RiskAssessor |
| UC-162 | Valida LLMOps (híbrido) | Input para RiskAssessor |
| UC-325 | Auto-reflexión (deliberativo) | Input para RiskAssessor |
| UC-322 | Resuelve conflictos (BDI) | Input para RiskAssessor |
| UC-329 | Graph reasoning (deliberativo) | Input para DossierBuilder |

### Flujo de integración

```text
UC-315 decide → UC-290 HITL revisa
                    ├── UC-087: ¿integridad OK?
                    ├── UC-162: ¿LLMOps OK?
                    ├── UC-325: ¿reflexión OK?
                    ├── UC-322: ¿conflictos?
                    ├── UC-329: ¿razonamiento?
                    │
                    ├── Riesgo bajo → auto-execute → UC-317
                    └── Riesgo alto → expediente → humano
                                           ├── approve → UC-317
                                           ├── modify → UC-317
                                           └── reject → bloquear
```

### Principio: "Un modelo genera evidencia. La evidencia no es una orden."

UC-315 genera una sugerencia (evidencia). UC-290 evalúa esa evidencia. Si el riesgo es alto, la evidencia se convierte en un expediente para revisión humana. Solo después de la aprobación humana (o auto-execute de bajo riesgo), la evidencia se convierte en una orden para UC-317.

> **Principio clave UC-290**: Un modelo genera evidencia. La evidencia no es una orden.
