# DESCRIPTION
UC-300 implementa un **Secure Tool Gateway** con un **Pre-Intent Gate determinista** situado *antes* de UC-315. El objetivo es neutralizar los riesgos de intenciones de usuario maliciosas o ambiguas lo más temprano posible, sin romper la compatibilidad del gateway existente:

```
Usuario → UC-300 Pre-Intent Gate → UC-315 → UC-290 → UC-300 Tool Gateway → UC-317 → UC-324
                ↑
        UC-309 transversal (observabilidad)
                ↓
        UC-308 histórico (contexto/auditoría)
```

- **UC-300 Pre-Intent Gate**: normaliza, valida, clasifica y decide `ALLOW` / `BLOCK` / `ESCALATE` sobre la intención bruta del usuario.
- **UC-315**: propone la acción concreta de herramienta.
- **UC-290**: evalúa riesgo y aprueba/escala.
- **UC-300 Tool Gateway**: autoriza la llamada exacta con capability token.
- **UC-317**: ejecuta en sandbox.
- **UC-324**: contiene/aisla si es necesario.

La suite cubre pre-filtrado de intenciones, normalización Unicode, detección de evasión/manipulación, mandatos deny-by-default por agente/tenant/dominio, escalamiento ligado a `intent_hash`, autorización, acceso cross-tenant, inyección, validación semántica, aprobación humana, alteración de parámetros, expiración, replay, idempotencia, cuotas, sandbox, kill switch, auditoría inmutable, métricas, eventos canónicos y API.

1. **Acceso no autorizado:** un agente es engañado o forzado a actuar sobre recursos que no le pertenecen.
2. **Inyección de comandos/prompts:** un actor malicioso introduce payloads en parámetros o instrucciones para ejecutar acciones no deseadas.

Veredictos `ALLOW`, `BLOCK`, `ESCALATE`; `ALLOW` solo para intenciones dentro del mandato y bajo riesgo.

Aprobación opcional ligada exactamente al `intent_hash` para resolver escalamiento sin invocar red.
Emisión desacoplada/callback a UC-309 con evento canónico seguro (`thought_summary`); almacén local inmutable; sin texto crudo, secretos ni chain-of-thought.
Validación estricta con esquemas versionables y rechazo de campos adicionales.
Canonicalización y validación semántica de parámetros.
Detección defensiva de command, SQL y prompt injection.
Motor de políticas independiente con deny-by-default.
Autorización por agente, herramienta, recurso y entorno.
Credenciales opacas, temporales y de mínimo privilegio.
Capability tokens HMAC:
TTL.
Nonce.
Uso único.
Anti-replay.
Vinculación a agente, acción, parámetros y expediente UC-290.
Aprobación humana ligada al hash exacto de la acción.
Protección TOCTOU mediante revalidación antes de ejecutar.
Rate limits, presupuesto e idempotencia.
Kill switch externo.
Auditoría inmutable con cadena de hashes.
Sandbox simulado con herramientas allowlisted.
Validación de outputs.
Eliminaciones y pagos ejecutados exclusivamente como dry-run.
Sin acceso a shell, sistema de archivos, pagos o APIs reales.

La solución es **deny-by-default**, con dos pipelines estrictos:

**Pre-Intent Gate (antes de UC-315)**
```
user intent → normalize Unicode → validate identity/tenant/locale/age
            → injection/evasion detection → deterministic classification
            → mandate check (deny-by-default) → risk assignment
            → ALLOW / BLOCK / ESCALATE → canonical event + immutable audit
```

**Tool Gateway (autorización + ejecución)**
```
request → canonicalize → schema validation → injection detection
        → policy engine (RBAC + scopes) → quota/idempotency
        → risk/HITL check → capability token issuance
        → execute → TOCTOU revalidation → sandbox simulated handlers
        → output validation → immutable audit
```

No ejecuta shell, filesystem, pagos ni APIs reales. Todas las herramientas se ejecutan en un **sandbox simulado** con `dry-run` para operaciones destructivas.

# MACROPROCESS / PIPELINE

![diagrama_interconexion_completo](./diagrama_interconexion_completo_uc162_uc290_uc317_uc330_uc087.png)

## Fase 0: Pre-Intent Gate (`prefilter_intent`)

1. **Normalize**: Unicode NFKC, eliminar caracteres de control, colapsar whitespace.
2. **Validate**: tamaño, formato de `agent_id`, `tenant_id`, `locale`, `domain`, y edad del request.
3. **Evasion detection**: injection_detector existente + patrones de role override, ignore rules, encoding/obfuscation, data exfiltration y scope expansion.
4. **Classify**: reglas deterministas sobre palabras clave a las categorías `pricing_read/update`, `inventory_read/update`, `payment`, `deletion`, `secrets_access`, `permissions_change`, `external_publish`, `general_query`, `unknown`.
5. **Mandate**: deny-by-default por agente/tenant/dominio e intenciones permitidas.
6. **Risk**: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`.
7. **Verdict**:
   - `ALLOW`: dentro del mandato y riesgo bajo.
   - `BLOCK`: fuera de mandato, identidad inválida o malicioso/evasivo.
   - `ESCALATE`: sensible/ambiguo legítimo; genera payload estructurado para UC-290.
8. **Canonical event**: emisión a UC-309 vía adaptador desacoplado + store local inmutable; nunca texto crudo, secretos ni chain-of-thought.

## Fase 1: `authorize(request)`

1. **Canonicalize**: los parámetros se ordenan y normalizan para hashing determinista.
2. **Schema validation**: Pydantic valida tipos, rangos, regex y rechaza campos extra.
3. **Injection detection**: escaneo recursivo de strings contra patrones de comandos y prompt injection.
4. **Policy engine**: deny-by-default; solo permite lo declarado explícitamente y dentro del scope del agente.
5. **Quota/idempotency**: rate limit por agente, presupuesto para pagos, idempotencia por hash.
6. **Risk/HITL**: si la acción es destructiva (`delete_product`), pago alto (`send_payment > $5000`) o crítica, requiere aprobación humana explícita ligada al hash exacto.
7. **Capability token**: si todo pasa, se emite un token firmado con HMAC-SHA256, nonce único, TTL y vinculado a `action_hash` + `dossier_hash`.

## Fase 2: `execute(request, token)`

1. **Kill switch**: si está activado, bloquea inmediatamente.
2. **TOCTOU revalidation**:
   - Revalida esquema.
   - Recomputa `action_hash` y lo compara con el token.
   - Verifica firma, TTL, nonce no consumido, y binding a `dossier_hash`.
3. **Sandbox**: ejecuta handlers simulados.
4. **Output validation**: la salida cumple estructura esperada.
5. **Audit**: registro inmutable en hash chain.

# SUBPROCESSES

## Schema Registry

```python
class UpdatePriceParams(BaseModel):
    model_config = ConfigDict(extra="forbid")
    product_id: str = Field(..., pattern=r"^SKU-[0-9]{3}$")
    new_price: float = Field(..., gt=0.0)
    reason: str = Field(..., min_length=5, max_length=500)
```

- `extra="forbid"` rechaza parámetros no declarados.
- Los strings se normalizan (trim, uppercase para SKU).
- Los floats se redondean y se verifica finitud.

## Injection Detector

Escanea recursivamente agent_id, action y params. Patrones cubiertos:

- Inyección SQL: `; DROP TABLE`, `; DELETE FROM`, `--`, `/* ... */`.
- Inyección de shell: `$(...)`, backticks, `&&`, `||`, pipes, redirecciones a `/etc`, `eval`, `exec`, `rm`, `curl`, `wget`.
- Prompt injection: `ignore previous instructions`, `system prompt`, `jailbreak`, `DAN`, etc.

## Policy Engine

```python
engine.set_scope("agent_pricing_eu", ["SKU-001", "SKU-002"])
engine.add_rule(PolicyRule(
    identity="agent_pricing_eu",
    tool="update_price",
    resource="*",
    environment="default",
    effect="allow",
))
```

- Sin regla `allow` explícita, todo se deniega.
- Los scopes restringen recursos por agente.
- Se soportan reglas `deny` explícitas, condiciones por campo y entornos allowlistados.

## Capability Tokens

```python
token = mgr.issue(
    action_hash=action_hash,
    dossier_hash=dossier_hash,
    agent_id=agent_id,
    action=action,
    scopes=[action],
    ttl_seconds=300,
)
```

- HMAC-SHA256 firmado con secreto generado internamente (`secrets.token_hex`).
- `nonce` único; validación rechaza replay.
- TTL configurable; token rechazado si expiró.
- Vínculo exacto a `action_hash` y `dossier_hash`; cualquier cambio de parámetros rompe el token.

## Credential Broker

Emite credenciales opacas temporales (`lease_id`) vinculadas a un capability token y recurso. El secreto real se almacena interno; los logs y la API solo exponen handles.

## Quota Manager

- **Rate limit**: token bucket por `agent_id`.
- **Budget**: presupuesto diario para pagos.
- **Idempotency**: cachea resultados por hash de acción exacta.

## Sandbox Executor

Handlers allowlisted:

- `update_price`: modifica precio en estado simulado.
- `delete_product`: **dry-run**; nunca elimina del estado real.
- `send_payment`: **dry-run**; devuelve `transaction_id` simulado.
- `read_file`: lee desde un filesystem simulado en memoria (no accede a disco).

## Immutable Audit

Cada entrada referencia el hash de la anterior; alterar cualquier campo rompe `verify_chain()`. Soporta `tamper_check()` para detectar discrepancias.

# THREAT MODEL

| Amenaza | Mitigación |
|---------|------------|
| Intención maliciosa o ambigua desde el usuario | Pre-Intent Gate con normalización, validación, clasificación determinista y mandato deny-by-default. |
| Prompt injection / role override / ignore rules | injection_detector + patrones específicos de evasión en Pre-Intent Gate. |
| Obfuscación de payloads (base64, hex, URL encoding, zero-width) | Detección de encoding/obfuscation en Pre-Intent Gate. |
| Exfiltración de datos o expansión de scope | Patrones `data_exfiltration` y `scope_expansion` en Pre-Intent Gate. |
| Identidad/tenant spoofing | Validación de formato y allowlists de agent/tenant/domain en Pre-Intent Gate. |
| Replays de aprobaciones de intención | Aprobaciones consumidas y vinculadas exactamente al `intent_hash`. |
| Inyección SQL/shell en parámetros | Esquemas estrictos + injection detector. |
| Acceso cross-tenant | Policy engine deny-by-default + scopes. |
| Cambio de parámetros tras aprobación | Capability token vinculado a action_hash; TOCTOU revalidation. |
| Replay de token | Nonce one-use + idempotencia. |
| Token expirado o firmado con otro secreto | Verificación HMAC + TTL. |
| Bypass directo al executor | `execute()` requiere token válido; no hay API pública que ejecute sin authorize. |
| Fuga de secretos | Credential broker con handles opacos; token_secret nunca logueado. |
| Operaciones destructivas reales | Sandbox simulado con dry-run. |
| Apagado de emergencia | Kill switch externo en `/api/v1/kill-switch`. |
| Repudio | Audit hash chain inmutable (gateway + Pre-Intent Gate). |

# CONTROL / CONTINGENCY

- **Pre-Intent Gate**: `POST /api/v1/prefilter-intent` devuelve `ALLOW`/`BLOCK`/`ESCALATE`; solo `ALLOW` produce `ready_for_uc315`.
- **Aprobaciones de intención**: `POST /api/v1/prefilter-intent/approve` registra metadatos ligados exactamente al `intent_hash`; se consumen al usarse (anti-replay).
- **Kill switch**: `POST /api/v1/kill-switch {"enabled":true}` bloquea todas las operaciones de authorize/execute hasta desactivarse.
- **Reset**: `POST /api/v1/reset` limpia estado, tokens, cuotas, credenciales, audit, Pre-Intent Gate y kill switch.
- **Audit chain verification**: `GET /api/v1/audit-trail` incluye `chain_verified`; el Pre-Intent Gate mantiene su propia cadena inmutable.
- **No bypass**: no existe endpoint que ejecute sin token. `process()` es solo un helper interno para demos/tests; `process_user_request()` ejecuta únicamente el Pre-Intent Gate.

# TRACEABILITY / UC-290 INTEGRATION

## Pre-Intent Gate → UC-290

Cuando el Pre-Intent Gate emite `ESCALATE`, genera un payload estructurado:

```json
{
  "reason": "sensitive/high-risk intent within mandate (medium)",
  "intent_hash": "sha256...",
  "agent_id": "agent_pricing_eu",
  "tenant_id": "eu",
  "requested_capability": "update_price",
  "risk": "medium",
  "category": "pricing_update"
}
```

- El `intent_hash` es canónico y determinista (campos normalizados + capability).
- La aprobación humana puede registrarse localmente vía `approve_intent(intent_hash, reviewer_id, ...)` o el endpoint `/api/v1/prefilter-intent/approve`.
- Una vez aprobado, el mismo request reenviado con el mismo hash resuelve en `ALLOW` sin invocar red.
- Cada aprobación se consume al usarse (anti-replay).

## Tool Gateway → UC-290

UC-300 consume el expediente de UC-290:

- `dossier_id`: identificador del expediente.
- `dossier_hash`: hash de integridad del expediente.
- `dossier_status`: `approved`, `rejected`, `pending`.
- `reviewer_id`: quién aprobó.
- `approval_action_hash`: hash exacto de la acción aprobada.

Para acciones destructivas, pagos altos, permisos sensibles, publicaciones o manejo de secretos, UC-300 exige:

1. `dossier_status == "approved"`
2. `approval_action_hash == compute_action_hash(request)`
3. `dossier_hash` no vacío

Esto **impide cambiar parámetros después de la aprobación**.

# UC-309 INTEGRATION

El Pre-Intent Gate integra con UC-309 mediante un emisor desacoplado:

- Intenta importar `ObservabilityOrchestrator` de UC-309 de forma no transitiva; si no es importable, opera con un adaptador no-op/local.
- Cada decisión del Pre-Intent Gate emite un evento canónico de tipo `thought_summary` con:
  - `trace_id` / `span_id` / `agent_id` / `agent_version`.
  - `action_proposed` resumido (categoría, capability, summary).
  - `action_proposed_hash` = `intent_hash`.
  - `uc290` con `escalation=True` solo si el veredicto es `ESCALATE`.
  - `evidence_refs` de detecciones.
  - `labels` controlados (verdict, risk, category, locale).
- Nunca registra texto crudo, secretos ni chain-of-thought: la traza local inmutable almacena solo hashes, resúmenes redactados y referencias de evidencia.
