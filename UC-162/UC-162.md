# DESCRIPTION

En el contexto de **LLMOps**, el **modelado lógico de datos** (cómo estructuras conceptualmente los datos antes de su implementación física) es el punto donde se definen las reglas de **verificación de sesgos** y **seguimiento de linaje**. Estos controles no son "plugins" que se añaden después: son parte integral del diseño lógico.

---

## 1. Modelado lógico: ¿qué se modela en LLMOps?

A diferencia del modelado tradicional (tablas, relaciones, esquemas estáticos), en LLMOps el modelado lógico incluye:

| Capa lógica | Descripción | Ejemplo |
|-------------|-------------|---------|
| **Fuentes de datos** | Origen, propietario, frecuencia de actualización, nivel de sensibilidad | Documentos internos, web scraping, bases de conocimiento aprobadas |
| **Documentos/corpus** | Unidades de conocimiento con metadatos de gobernanza | Título, autor, fecha, dominio, versión, clasificación de confianza |
| **Chunks/segmentos** | Fragmentos procesables por el LLM con contexto preservado | Tamaño, overlap, estrategia de división (por párrafo, semántica) |
| **Embeddings** | Representaciones vectoriales con metadatos de generación | Modelo usado, fecha, parámetros, hash del texto origen |
| **Prompt context** | Conjunto de chunks recuperados + instrucciones + historial | Origen de cada chunk, score de relevancia, orden de inserción |

### Controles lógicos en la ingesta

| Control | Modelado lógico | Implementación |
|---------|-----------------|----------------|
| **Representatividad demográfica** | El esquema lógico define campos de `demografía_esperada` vs `demografía_observada` | Alerta si el corpus tiene >70% textos de un solo género/región/sector |
| **Balance de perspectivas** | Metadato `perspectiva` (técnica, ética, legal, económica) | Rechazar corpus donde una perspectiva supere el 80% |
| **Temporalidad** | Campo `periodo_temporal` en el esquema | Detectar si datos de 2020 dominan sobre 2025 en temas cambiantes |
| **Fuente y autoría** | `fuente_tipo`: académica, gubernamental, corporativa, crowd | Ponderar o filtrar según política de confianza |
| **Lenguaje y cultura** | `idioma`, `variante_regional`, `contexto_cultural` | Evitar que un dialecto o región domine sin justificación |

### Ejemplo de esquema lógico con controles de sesgo

```yaml
# schema_ingesta_corpus.yaml
version: "2.1"
name: corpus_soporte_cliente

campos_obligatorios:
  - id_documento
  - texto
  - fuente
  - fecha_creacion
  - categoria_tema

metadatos_gobernanza:
  - nombre: distribucion_demografica
    tipo: json
    reglas:
      - campo: genero_autor
        umbrales:
          maximo_dominancia: 0.70   # Ningún género >70%
          accion_si_excede: "flag_para_revision"
      
      - campo: region_geografica
        umbrales:
          maximo_dominancia: 0.60   # Máx 60% de una región
          accion_si_excede: "rechazar_lote"
      
      - campo: perspectiva_tematica
        tipo: enum: [tecnica, legal, etica, economica, social]
        reglas:
          minimo_por_tipo: 0.10     # Mínimo 10% cada perspectiva
          accion_si_falta: "enriquecer_con_fuentes_complementarias"

metricas_sesgo_calculadas:
  - nombre: disparidad_genero
    formula: "|pct_masculino - pct_femenino| / pct_no_binario"
    umbral_maximo: 2.0
    frecuencia_calculo: "por_lote"

  - nombre: concentracion_geografica
    formula: "entropia_shannon(regiones)"
    umbral_minimo: 1.5   # Mayor entropía = más diversidad
```

## 3. Seguimiento de linaje durante la preparación

### El linaje en LLMOps no es lineal: es un grafo

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  Documento  │────▶│   Chunk 1   │────▶│  Embedding  │────▶│  Recuperado │
│  Original   │     │  (párrafo)  │     │  (vector)   │     │  en RAG     │
│  [hash: A1] │     │  [hash: B2] │     │  [hash: C3] │     │  [hash: D4] │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
       │                   │                   │                   │
       └───────────────────┴───────────────────┴───────────────────┘
                           │
                    ┌──────▼──────┐
                    │  LINAJE     │
                    │  COMPLETO   │
                    │  (grafo)    │
                    └─────────────┘
```

### Metadatos de linaje modelados lógicamente

| Transformación | Metadatos capturados | Propósito |
|----------------|----------------------|-----------|
| **Ingesta** | `fuente_url`, `fecha_extraccion`, `metodo_scraping`, `hash_md5_original` | Trazabilidad legal, verificación de integridad |
| **Limpieza** | `script_limpieza_v2.3`, `reglas_aplicadas` (HTML stripping, normalización), `tokens_antes/después` | Reproducibilidad, auditoría de pérdida de información |
| **Chunking** | `estrategia`: semántica/fija/recursiva, `tamano_chunk`, `overlap`, `modelo_chunker` | Optimización de RAG, debugging de contexto perdido |
| **Embedding** | `modelo_embedding` (text-embedding-3), `dimension`, `fecha_generacion`, `hardware` | Comparabilidad de retrieval, cost tracking |
| **Indexación** | `vector_store` (Pinecone/Weaviate), `indice_nombre`, `shard`, `replicacion` | Disaster recovery, migraciones |
| **Recuperación (RAG)** | `query_original`, `query_expandida`, `top_k`, `score_similitud`, `chunks_recuperados` (lista de IDs) | Debugging de alucinaciones, explicabilidad |

## 6. Resumen: el modelado lógico como contrato de gobernanza

| Aspecto | ¿Qué se modela lógicamente? | ¿Quién lo define? |
|---------|----------------------------|-------------------|
| **Sesgos** | Umbrales de representatividad, métricas de fairness, acciones ante desviación | Data Ethics Officer + Domain Expert |
| **Linaje** | Esquema de metadatos obligatorios en cada transformación, hashes de integridad, grafo de relaciones | Data Architect + Compliance |
| **Calidad** | Reglas de validación (completitud, formato, consistencia), score mínimo de confianza | Data Engineer + QA |
| **Acceso** | RBAC sobre quién puede ver/modificar cada capa del linaje | Security + Legal |

> **Principio clave**: En LLMOps, el modelado lógico no es solo "cómo se ven los datos", sino **"cómo se garantiza que los datos que alimentan al LLM son trazables, justos y auditables en cada transformación"**. Sin este modelado, no hay explicabilidad ni defensa ante alucinaciones o sesgos sistémicos.

# Implementación UC-162 — LLMOps Governance Layer

## 7. Alcance y objetivo

UC-162 es una **capa externa de gobernanza LLMOps** que valida las propiedades semánticas, conceptuales, lógicas y de sesgo de los datos y modelos que alimentan a UC-315. Se diferencia de UC-087 en:

| Pregunta | UC-087 | UC-162 |
|----------|--------|--------|
| ¿Los datos fueron manipulados? | Sí | No |
| ¿Los datos están conceptualmente bien estructurados? | No | Sí |
| ¿Hay sesgo en el diseño lógico? | No | Sí |
| ¿Hay hallucination en los outputs? | No | Sí |
| ¿Hay drift conceptual? | No | Sí |
| ¿El linaje semántico se preservó? | No | Sí |
| ¿Los prompts están versionados y aprobados? | No | Sí |

**Principio de autoridad**: UC-315 decide, UC-317 ejecuta, UC-324 contiene, UC-322 resuelve conflictos. UC-162 **valida** pero no ejecuta ni contiene. Un modelo genera evidencia; la evidencia no es una orden.

## 10. Subprocesos

### SP-162-01: Validación de esquema lógico

1. Recibir corpus de documentos.
2. Para cada documento, validar campos obligatorios del esquema.
3. Verificar que los metadatos de gobernanza estén presentes.
4. Reportar issues de estructura.
5. Si hay issues críticos → flag para revisión.

### SP-162-02: Verificación de sesgo

1. Calcular distribución de `genero_autor` (dominancia máx 0.70).
2. Calcular distribución de `region_geografica` (dominancia máx 0.60).
3. Calcular distribución de `perspectiva_tematica` (dominancia máx 0.80, representación mín 0.10).
4. Calcular distribución de `periodo_temporal` (dominancia máx 0.65).
5. Calcular distribución de `fuente_tipo` (dominancia máx 0.75).
6. Calcular distribución de `idioma` (dominancia máx 0.95).
7. Calcular métricas: entropía de Shannon, disparidad de género.
8. Generar acciones: pass, flag_for_review, reject_lot, enrich_with_complementary_sources.
9. Agregar decisión: all_passed = True/False.

### SP-162-03: Registro de linaje semántico

1. Para cada documento ingerido → registrar nodo `ingest` con hash SHA-256.
2. Para cada transformación → registrar nodo con stage, entity_id, hash, parent_hash.
3. Construir grafo de nodos y aristas.
4. Para cada respuesta del LLM → registrar nodo `generate` con parent_hash del retrieval.
5. Permitir trazabilidad inversa (trace_back) desde cualquier nodo hasta la raíz.

### SP-162-04: Detección de hallucination

1. Recibir respuesta del LLM y chunks recuperados.
2. Tokenizar respuesta y chunks.
3. Calcular cobertura: qué fracción de tokens de la respuesta están en los chunks.
4. Identificar claims no soportados (oraciones sin overlap con chunks).
5. Identificar chunks no contribuyentes (que no aportan tokens a la respuesta).
6. Calcular score de coherencia.
7. Asignar severidad: none, low, medium, high, critical.
8. Decidir: is_hallucination = True si severidad >= high o coverage < 0.3.

### SP-162-05: Versionado de prompts

1. Registrar prompt con template, versión, tags, metadata.
2. Evaluar prompt con score 0-1.
3. Aprobar prompt (approved_by, timestamp).
4. Mantener historial de acciones (registered, evaluated, approved).
5. Consultar prompts aprobados, latest approved, por versión.

### SP-162-06: Detección de drift conceptual

1. Establecer baseline para un concepto (contextos + co-ocurrencias).
2. Recibir observación actual (contextos + co-ocurrencias).
3. Calcular distribución de contextos baseline vs actual.
4. Calcular distancia JS (Jensen-Shannon) entre distribuciones.
5. Calcular drift de co-ocurrencias (Jaccard distance).
6. Combinar scores: drift_score = 0.6 * context_drift + 0.4 * co_occurrence_drift.
7. Clasificar tipo: none, contextual, co_occurrence, combined.
8. Decidir: is_drift = True si drift_score > threshold (default 0.3).

### SP-162-07: Orquestación del guardian

1. **process_corpus**: validar esquema → verificar sesgo → registrar linaje → decidir.
2. **evaluate_response**: detectar hallucination → registrar linaje de generación → decidir.
3. **check_drift**: comparar contra baseline → decidir.
4. **register_prompt / approve_prompt / evaluate_prompt**: gestionar prompts.
5. Decisión final:
   - `approve`: todas las verificaciones pasan.
   - `flag`: verificaciones pasan con advertencias.
   - `reject`: sesgo crítico o hallucination crítica.
   - `escalate`: drift conceptual detectado, requiere intervención humana.

## 12. Modelo lógico

### Esquema conceptual (`LogicalSchema`)

| Campo | Tipo | Descripción |
|-------|------|-------------|
| `version` | str | Versión del esquema (default: "2.1") |
| `required_fields` | list | Campos obligatorios: id_documento, texto, fuente, fecha_creacion, categoria_tema, genero_autor, region_geografica, perspectiva_tematica, idioma, periodo_temporal |
| `bias_thresholds` | dict | Umbrales de sesgo por campo |
| `lineage_stages` | list | Etapas de linaje: ingest, clean, chunk, embed, index, retrieve, generate |

### Umbrales de sesgo

| Campo | Dominancia máx | Acción si excede |
|-------|---------------|------------------|
| `genero_autor` | 0.70 | flag_for_review |
| `region_geografica` | 0.60 | reject_lot |
| `perspectiva_tematica` | 0.80 | flag_for_review |
| `perspectiva_tematica_representation` | 0.10 (mín) | enrich_with_complementary_sources |
| `periodo_temporal` | 0.65 | flag_for_review |
| `fuente_tipo` | 0.75 | flag_for_review |
| `idioma` | 0.95 | flag_for_review |

### Métricas calculadas

| Métrica | Fórmula | Umbral |
|---------|---------|--------|
| `entropia_shannon_regiones` | H(regiones) | mín 1.5 |
| `entropia_shannon_perspectivas` | H(perspectivas) | mín 1.5 |

| `entropia_shannon_temporal` | H(periodos) | mín 1.0 |

## 13. Reglas de sesgo

### Controles implementados

| Control | Tipo | Descripción |
|---------|------|-------------|
| Representatividad demográfica | `demographic` | Ningún género > 70% del corpus |
| Concentración geográfica | `demographic` | Ninguna región > 60% del corpus |
| Dominancia de perspectiva | `perspective` | Ninguna perspectiva > 80% del corpus |
| Representación de perspectiva | `perspective` | Cada perspectiva >= 10% del corpus |
| Balance temporal | `temporal` | Ningún periodo > 65% del corpus |
| Diversidad de fuentes | `source` | Ningún tipo de fuente > 75% del corpus |

### Acciones

## 14. Linaje semántico

### Etapas del linaje

| Etapa | Descripción | Metadatos capturados |
|-------|-------------|---------------------|
| `ingest` | Ingesta de documento | source, source_url, extraction_method, text_length |
| `clean` | Limpieza de texto | cleaning_rules, tokens_before, tokens_after |
| `chunk` | Segmentación | chunk_strategy, chunk_size, overlap |
| `embed` | Embedding | model, dimension, text_hash |
| `index` | Indexación | vector_store, index_name |
| `retrieve` | Recuperación RAG | query, top_k, chunk_ids |
| `generate` | Generación de respuesta | response_length, prompt_version, model |

### Trazabilidad

Cada nodo del linaje incluye:
- `node_id`: UUID único.
- `stage`: etapa del pipeline.
- `entity_id`: identificador de la entidad.
- `hash`: SHA-256 del contenido + metadatos.
- `parent_hash`: hash del nodo padre (para construir el grafo).
- `metadata`: metadatos específicos de la etapa.
- `timestamp`: momento de registro.

El método `trace_back(hash)` permite recorrer el linaje desde cualquier nodo hasta la raíz.

## 15. Controles de hallucination

### Algoritmo

1. **Tokenización**: la respuesta y los chunks se dividen en tokens (palabras en minúsculas).
2. **Cobertura**: fracción de tokens de la respuesta presentes en los chunks.
3. **Claims no soportados**: oraciones de la respuesta sin overlap con chunks.
4. **Chunks no contribuyentes**: chunks que no aportan tokens a la respuesta.
5. **Severidad**:
   - `none`: coverage >= 0.7, sin claims no soportados.
   - `low`: coverage >= 0.5, 1-2 claims no soportados.
   - `medium`: coverage >= 0.3, claims no soportados.
   - `high`: coverage < 0.3 o respuesta vacía.
   - `critical`: sin chunks o respuesta vacía.
6. **Decisión**: `is_hallucination = True` si severidad >= high.

## 17. Drift conceptual

### Distinción: drift conceptual vs drift estadístico

| Aspecto | Drift estadístico | Drift conceptual |
|---------|------------------|------------------|
| Qué detecta | Cambios en distribución de valores | Cambios en significado semántico |
| Cómo detecta | KS test, PSI, chi-cuadrado | Distancia JS sobre contextos + co-ocurrencias |
| Ejemplo | La media de edad cambia de 30 a 45 | "Spread" pasa de significar bid-ask a volatilidad |
| Falso negativo | Distribución estable pero significado cambiado | Detecta cambio de significado aunque distribución sea estable |

### Algoritmo

1. **Baseline**: distribución de contextos + co-ocurrencias para un concepto.
2. **Observación actual**: nueva distribución de contextos + co-ocurrencias.
3. **Context drift**: distancia Jensen-Shannon entre distribuciones de contextos.
4. **Co-occurrence drift**: distancia Jaccard entre conjuntos de co-ocurrencias.
5. **Drift score combinado**: `0.6 * context_drift + 0.4 * co_occurrence_drift`.
6. **Tipo de drift**: none, contextual, co_occurrence, combined.
7. **Decisión**: `is_drift = True` si `drift_score > threshold` (default 0.3).

## 19. Integración con UC-315

### Boundary

- UC-315 es el **consumidor final** del conocimiento validado.
- UC-315 **no** gobierna sus propios controles de seguridad (UC-087).
- UC-315 **no** gobierna sus propios controles semánticos (UC-162).
- UC-315 **solo recibe** conocimiento si ambas capas externas aprueban.
- Un modelo genera evidencia; la evidencia no es una orden.

### Contrato de consumo

UC-315 puede consumir un conocimiento/modelo actualizado solo si:
1. UC-162 devuelve `decision = "approve"`.
2. UC-087 devuelve `decision = "approve"` (o equivalente).
3. No hay issues críticos pendientes.
4. El linaje semántico está completo y trazable.
