# DESCRIPTION

## 1. Objetivo

UC-274 implementa un **ecosistema descentralizado Web3 para sistemas multi-agente** con blockchain Byzantine-Fault-Tolerant (BFT). Los agentes tienen wallets, identidades descentralizadas (DIDs) y reputación on-chain. Los contratos inteligentes permiten comercio P2P de energía, pagos condicionales (escrow), reputación y liquidación — todo sin autoridad central.

## 2. Las 4 Capas de la Arquitectura

### Capa 1: Identidad Web3 (Wallets + DIDs)

- **Wallet Ed25519**: keypair de alta performance. Dirección derivada: `SHA-256(public_key)[:20 bytes]` con prefijo `0x`.
- **DID (Decentralized Identifier)**: formato `did:mustiamente:<address>` según W3C DID Core v1.
- **DID Document**: método de verificación `Ed25519VerificationKey2020`, autenticación, metadata.
- **DIDRegistry**: registro/resolución on-chain de DIDs, con nombres ENS-like (`@name.mustiamente → address`).

### Capa 2: Consenso BFT (PBFT-lite)

Protocolo de consenso Byzantine-Fault-Tolerant con 4 fases:

1. **PRE-PREPARE**: proposer envía bloque a todos los validadores.
2. **PREPARE**: validadores verifican integridad y votan (firma Ed25519).
3. **COMMIT**: tras recibir `2f+1` PREPARE, se envía COMMIT.
4. **DECIDE**: tras `2f+1` COMMIT, el bloque es final (determinístico).

**Tolerancia**: `f` fallos byzantinos con `n = 3f+1` validadores.
- Con 4 validadores: tolera 1 byzantino.
- Con 7 validadores: tolera 2 byzantinos.

Los validadores byzantinos pueden: no votar, votar por bloques falsos, o enviar votos conflictivos. El protocolo garantiza safety (nunca se aceptan 2 bloques conflictivos) y liveness (siempre se alcanza consenso si `<= f` validadores son maliciosos).

### Capa 3: Smart Contracts

4 contratos inteligentes desplegados automáticamente:

| Contrato | Dirección | Funcionalidad |
|---|---|---|
| **EnergyTradeContract** | `0xenergy_contract` | Ofertas buy/sell de energía, matching, escrow automático, confirmación de entrega por oracle |
| **EscrowContract** | `0xescrow_contract` | Pagos condicionales con timeout, release por depositor, refund automático al expirar |
| **ReputationContract** | `0xreputation_contract` | Reputación on-chain bayesiana, record de trades, endorsements entre agentes |
| **SettlementContract** | `0xsettlement_contract` | Liquidación de trades con fees, contabilidad de comisiones |

### Capa 4: Aplicación (Energy Marketplace)

El **EnergyMarketplace** orquesta todo el ecosistema:
- Registra agentes (wallet + DID + ENS name + balance inicial).
- Gestiona ofertas de energía P2P (solar, wind, hydro, biomass, grid).
- Matchea compras con ofertas (crea escrow automático).
- Oracle confirma entrega y libera escrow.
- Reputación on-chain con endorsements ponderados.
- Blockchain explorer: bloques, transacciones, verificación de cadena.

# API

## Card Views — Entrada

### `POST /api/v1/agent/register`
Registra agente con wallet Ed25519, DID y nombre ENS-like.
```json
{"name": "solar_farm_alpha", "initial_balance_wei": 1000000, "metadata": {"role": "prosumer"}}
```

### `POST /api/v1/energy/offer`
Crea oferta de compra/venta de energía P2P.
```json
{
  "agent_name": "solar_farm_alpha",
  "side": "sell",
  "quantity_kwh": 50.0,
  "price_per_kwh_wei": 800,
  "energy_source": "solar"
}
```

### `POST /api/v1/energy/match`
Compra energía matcheando una oferta existente (crea escrow automático).
```json
{"buyer_name": "household_gamma", "offer_id": "abc123...", "quantity_kwh": 20.0}
```

### `POST /api/v1/energy/confirm`
Oracle confirma entrega de energía y libera escrow al vendedor.
```json
{"trade_id": "xyz789..."}
```

### `POST /api/v1/escrow/create`
Crea escrow de pago condicional con timeout.
```json
{
  "depositor_name": "battery_delta",
  "beneficiary_name": "solar_farm_alpha",
  "amount_wei": 100000,
  "condition": "deliver 10 kWh"
}
```

### `POST /api/v1/escrow/release`
Libera fondos del escrow al beneficiario.
```json
{"caller_name": "battery_delta", "escrow_id": "esc123..."}
```

### `POST /api/v1/reputation/record`
Registra trade exitoso o disputa en reputación on-chain.
```json
{"trader_name": "solar_farm_alpha", "success": true}
```

### `POST /api/v1/reputation/endorse`
Endosa reputación de otro agente (peso proporcional a reputación del endorser).
```json
{"endorser_name": "solar_farm_alpha", "target_name": "wind_farm_beta", "score": 0.8}
```

### `POST /api/v1/blockchain/mine`
Mina un bloque con consenso BFT (PBFT-lite).
```json
{"validator_index": 0}
```

## 6. Blockchain y Web3 para Confianza en Multi-Agente

### Por qué blockchain mejora la confianza en ecosistemas de agentes

- **Transparencia**: todas las transacciones son visibles y verificables por todos los agentes. Ningún agente puede alterar el historial.
- **Inmutabilidad**: la cadena de hashes SHA-256 y el Merkle root de transacciones garantizan que ninguna entrada puede modificarse sin invalidar bloques posteriores.
- **Confianza descentralizada**: el consenso BFT (PBFT-lite) no depende de una autoridad central. La confianza emerge del protocolo mismo: si `>2/3` de los validadores son honestos, el sistema es seguro.
- **Smart Contracts**: permiten ejecutar acuerdos automáticamente (escrow, settlement, reputación) sin intermediarios.
- **Identidades digitales (DIDs)**: cada agente tiene una identidad criptográfica única verificable, con reputación on-chain que se construye mediante trades exitosos y endorsements.

### Comercio descentralizado de energía

El caso de uso principal demuestra cómo agentes prosumidores (hogares con paneles solares, granjas eólicas) pueden:
1. **Publicar ofertas** de venta/compra de energía.
2. **Matchear trades** P2P con escrow automático.
3. **Confirmar entregas** vía oracles de medición.
4. **Liquidar pagos** con fees transparentes.
5. **Construir reputación** on-chain que persiste y es inmutable.

## 7. Consenso BFT — Tolerancia a fallos byzantinos

```
Validadores: [V1, V2, V3, V4]
n = 4, f = 1 (tolerancia), required = 2f+1 = 3

PRE-PREPARE:  V1 (proposer) → broadcast bloque
PREPARE:      V2 ✓, V3 ✓, V4 ✗ (byzantino)  →  2 PREPAREs ≥ 2 (required-1)
COMMIT:       V1 ✓, V2 ✓, V3 ✓               →  3 COMMITs ≥ 3 (required)
DECIDE:       Bloque FINAL ✓
```

El bloque se acepta a pesar de V4 ser malicioso, porque se alcanzó quorum de `2f+1 = 3` votos honestos.
